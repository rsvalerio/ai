# UNSAFE rules

## Unsafe (typical severity: High--Critical)

- **UNSAFE-1.** Small `unsafe` blocks; document invariants with `// SAFETY:` comments. For performance micro-optimization (e.g., `get_unchecked`), only apply after profiling confirms the bottleneck
- **UNSAFE-2.** `unsafe fn` only if every call requires upholding invariants — and specifically invariants whose violation is **undefined behaviour**. `unsafe` is not a general danger marker: `unsafe fn delete_database()` is a misuse that trains readers to skim past the keyword, which is the one thing it must never do. A function that is merely destructive, expensive, or easy to misuse is a *safe* function with a loud name and a `# Panics`/doc warning (API-14). Conversely, a safe-looking function with any UB-producing calling mode is unsound and must be marked `unsafe` regardless of how remote that mode is (UNSAFE-11)
- **UNSAFE-3.** Use `std::ptr` utilities over raw arithmetic
- **UNSAFE-4.** Test unsafe code thoroughly
- **UNSAFE-5.** Wrap unsafe in safe public APIs, and put the unsafe code in the smallest *module* that can uphold the invariant — not merely the smallest block (UNSAFE-1). The unit of audit is the privacy boundary, not the `unsafe` keyword: if the invariant is "the first `len` bytes are initialized", then every function able to write `len` or the buffer belongs inside that module, and everything outside it is code nobody has to re-review for soundness. `std`'s `String` is the model — a private `Vec<u8>` plus the UTF-8 invariant, every safe operation preserving it, and the invariant-transferring constructors named (`from_utf8_unchecked`) so the caller sees the obligation it is taking on. A module that leaves the field `pub(crate)` has contained nothing: the audit surface is the whole crate again. The outer module may still expose `unsafe` fast paths that call in directly (UNSAFE-2); what it must not do is let safe code outside the boundary reach the representation
- **UNSAFE-6.** *Not a finding rule.* `unsafe extern` blocks are enforced by the Rust 2024 edition and migrated by `cargo fix --edition`; documented here for reviewer awareness only.
- **UNSAFE-7.** *Not a finding rule.* `#[unsafe(...)]` attribute syntax is enforced by the Rust 2024 edition and migrated by `cargo fix --edition`; documented here for reviewer awareness only.
- **UNSAFE-8.** `std::env::set_var`/`remove_var` are unsafe in 2024 edition; avoid in async contexts
- **UNSAFE-9.** Never guard an `unsafe` precondition with `debug_assert!` alone. `debug_assert!` compiles to nothing when `debug_assertions` is off — which is the default for `--release` — so a bounds or nullity check that "passes in CI" silently vanishes in the shipped binary, turning a caught bug into UB. Use `assert!` (unconditional) for any condition whose violation causes unsoundness; reserve `debug_assert!` for expensive sanity checks on *safe* internal invariants where the failure mode is a wrong answer, not memory unsafety. Same reasoning applies to security checks — see SEC-31 (fail closed)
- **UNSAFE-10.** `unsafe` needs a stated reason from a short list, and evidence. The only reasons that hold up are: a novel abstraction that cannot be built safely (a smart pointer, an allocator, a data structure with internal aliasing), a **measured** performance need (`get_unchecked` after a profile showed the bounds check mattered, PERF-6), and FFI or platform calls. What is not a reason: shortening safe code that already works, casting an enum with `transmute` instead of a `From` impl (SEC-3), or bypassing a bound the compiler is enforcing for cause — `unsafe impl Send for Wrapper<T> {}` to silence a `!Send` field is the canonical unsound "fix" (TRAIT-13, SEC-4). Where `unsafe` is justified, three checks are the finding when absent: (1) every block carries `// SAFETY:` prose stating which invariant makes it sound (UNSAFE-1; `clippy::undocumented_unsafe_blocks` enforces presence, not quality); (2) the code is exercised under **Miri** (`cargo +nightly miri test`) — Miri catches aliasing, alignment, and provenance violations that pass every ordinary test; (3) an abstraction that accepts caller-supplied closures or types is tested against **adversarial** behaviour, because a safe trait impl may misbehave without being unsound itself: a `Deref` returning a different target each call, a `Clone` that panics, a `Drop` that re-enters your type, a closure that unwinds mid-operation. If a panic from user code can leave your invariant broken, the type must poison itself rather than continue (ERR-15)
- **UNSAFE-11.** Distinguish *unsafe* from *unsound*, because the review question differs. A function is `unsafe` if it is marked so; it is **unsound** if it is *not* marked and yet some calling pattern — any pattern, however contrived, using only safe code — causes undefined behaviour. `fn as_u128<T>(x: &T) -> &u128 { unsafe { transmute(x) } }` is a safe signature over UB and is unsound; `vec.get_unchecked(i)` is `unsafe` and perfectly benign when its contract is met. Unsoundness is the one thing in these rules with no severity discount and no justified-violation exception (rules-classification): if the abstraction cannot be made sound, expose an `unsafe fn` with a documented contract instead of a safe wrapper. The scope that matters is the **module**: soundness is judged over everything that can construct or mutate the type, so a private field upheld by every function in the module may be relied on by a safe method that cannot itself verify it — which is exactly why adding a `pub` field, a new constructor, or a `#[derive]` to such a type can make previously sound code unsound without touching the `unsafe` block. Treat any change that widens construction or mutation of an invariant-bearing type as touching its unsafe code
- **UNSAFE-12.** A crate that does not need `unsafe` should say so mechanically: `unsafe_code = "forbid"` in the crate's `[lints.rust]` table (or inherited from `[workspace.lints]`, ARCH-11), or `#![forbid(unsafe_code)]` in the crate root. `forbid` rather than `deny` is the point — it cannot be lifted by a later `#[allow(unsafe_code)]` on a module or function, so the property survives the well-meaning PR that adds one `unsafe` block for a micro-optimization, and it turns "does this crate contain unsafe?" into a fact the build enforces rather than a question a reviewer re-answers. In a workspace, most member crates should carry it; the FFI, `-sys`, and low-level crates that genuinely cannot are then a short, visible list, which is exactly the list a soundness review should cover (UNSAFE-5, ARCH-14). Note this is not the `#![deny(warnings)]` mistake (ARCH-18): that lint's set changes with every compiler release, while `unsafe_code` is a single stable lint whose meaning does not drift. Two real costs before recommending it: `forbid` also rejects `unsafe` tokens a macro the crate invokes expands into this crate — the lint applies to the crate being compiled, not to the dependency's own separately compiled code, and a macro marked `allow_internal_unsafe` is exempt — and it forbids the `unsafe(...)` attribute wrapper the 2024 edition requires on `#[no_mangle]`/`#[export_name]`/`#[link_section]` (UNSAFE-7) — a crate that needs either wants `deny` plus a scoped `#[expect(unsafe_code, reason = "…")]` (READ-10) instead of dropping the lint entirely
