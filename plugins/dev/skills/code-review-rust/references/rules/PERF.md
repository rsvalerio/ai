# PERF rules

## Performance (typical severity: Medium)

- **PERF-1.** Avoid premature `.collect()` — keep data as iterators through chains and collect only at the final consumption point; unnecessary intermediate collections waste allocations and defeat lazy evaluation. Note: basic indexed-loop-to-iterator conversion is handled by `clippy::needless_range_loop`
- **PERF-2.** `Vec::with_capacity()` when size known — eliminates reallocations in hot paths. Applies to every growable collection (`String`, `HashMap`, `HashSet`, `VecDeque`), and an approximate size is enough: a `push` loop over a source of known length reallocates and copies log₂(n) times for nothing. Note `collect()` already does this via the iterator's `size_hint`, so `let v: Vec<_> = src.iter().map(f).collect();` is both the tidier and the faster spelling of a `with_capacity` + `push` loop — reach for the explicit capacity when the loop cannot be an iterator chain
- **PERF-3.** Avoid `.clone()` in hot paths; use `Option::take()` or `std::mem::replace()` to move instead of copy (see also OWN-8 for general clone guidance). **"Hot path" is load-bearing, and the inverse is also a finding.** Rust makes allocation costs unusually visible, which pushes reviewers and authors toward eliminating every one of them — but complexity added to avoid an allocation in code that is not performance-critical is a net loss, and it is the more common error of the two in application code. A `.clone()`, an `Arc`, or a `Vec` where a borrow or a `&[T]` "would do" is the right call when it keeps a lifetime out of a signature, keeps a struct non-generic, or keeps a function readable; startup paths, configuration loading, CLI argument handling, error construction, test setup, and anything running once per request rather than once per byte are all cold enough that the trade is free. Flag the *reverse* shape too: a lifetime parameter, a `Cow`, a hand-rolled arena, or an unsafe block introduced for an allocation nobody profiled (PERF-6). The order of operations is write it simply, profile, then optimize the one or two paths that showed up — and Rust is specifically good at letting that second step happen later, so the cost of deferring is low (ARCH-6)
- **PERF-4.** `Option::take()` for safe resource cleanup; prevents double drops when moving out of `Option`
- **PERF-5.** `#[inline]` exposes a function's body to cross-crate inlining (non-generic functions are otherwise monomorphized in the defining crate only). Within a crate, LLVM inlines across codegen units only with LTO or `codegen-units = 1`; otherwise cross-CGU calls are opaque. Use `#[inline]` on small, hot, cross-crate functions; use `#[inline(always)]` sparingly and only when profiling confirms it. Generic functions and `#[inline]` functions are inlined at the call site by default
- **PERF-6.** Benchmark release builds only — debug builds disable optimizations and produce misleading numbers (5--20x slower). Tools: `criterion` (via `cargo criterion`) or `divan` for benchmarks, `cargo flamegraph` for CPU profiling, `tokio-console` for async task diagnostics; on Windows, Intel VTune and Superluminal work against Rust binaries directly. Benchmarks need symbols to be readable in a profiler — set `[profile.bench] debug = 1`. Prefer measuring CPU time across all threads alongside wall time where you can: a change that moves work onto more cores looks like a win on wall time and is a regression on cost. Decide early whether the crate is performance- or cost-relevant; if it is, build the benchmarks around the hot paths *before* optimizing, and write down (in module docs or the README) which areas are performance-sensitive, so the next contributor does not undo the work. Workflow: profile → identify 1--2 dominant hotspots (typically 80% of cycles) → optimize those → measure again; never optimize without profiling first
- **PERF-7.** Prefer pass-by-value for small `Copy` types (≤16 bytes, roughly two machine words) in inner loops — indirection through `&T` adds a load per access and inhibits register allocation. `clippy::trivially_copy_pass_by_ref` and `large_types_passed_by_value` flag the obvious cases; this rule's unique value is the hot-loop judgment: profile before restructuring wide signatures
- **PERF-8.** Fast hashers (`ahash` via `HashMap` from `hashbrown`, `FxHashMap`, `XxHash64`) for internal maps where keys are trusted (not user-supplied); default `SipHash` is collision-resistant and needed for untrusted keys to prevent HashDoS; `ahash` is the most common ecosystem choice (used by `DashMap`), and `foldhash` is the current default in `hashbrown` 0.15+ — either is a reasonable pick, and the swap is a type-alias change (`foldhash::HashMap<K, V>`), not a rewrite
- **PERF-9.** `SmallVec` when collections are typically small (stack-allocated up to N, spills to heap); `ArrayVec` for hard upper bounds (compile-time capacity). Sweet spot: 1--4 elements typical; beyond ~8, heap `Vec` is usually better
- **PERF-10.** `rayon::par_iter()` for data parallelism on CPU-bound iterators. Sync code only; for async, use `spawn_blocking` + rayon. Not beneficial for I/O-bound or small workloads
- **PERF-11.** Reuse buffers across loop iterations with `.clear()` instead of re-allocating. This is also an **API-design** obligation, not only a local one: a signature that returns a fresh allocation per call (`fn get(&self, id: Id) -> Value`) forces an allocation on every iteration of the caller's loop and gives them no way out. Offer a fill-into form alongside it — `fn get_into(&self, id: Id, out: &mut Value)` — so the caller owns the buffer and decides when to allocate (API-7 permits out-params for exactly this). In deeply nested or allocation-heavy call stacks, threading a bump arena through a caller-owned context struct achieves the same at one level up (PATTERN-5). The convention `std` establishes is `.clear()` to make a value reusable; follow it on your own reusable types
- **PERF-12.** Replace linear scans with composed maps (`HashMap<K, BTreeMap<...>>`) for O(1)+O(log n) lookup when data has two-level keys; adds memory overhead — profile to confirm benefit
- **PERF-13.** Build formatted output with `write!`/`writeln!` directly into the destination instead of `format!` + `push_str`/`write_all` — the intermediate `String` is a wasted allocation per call. This is mandatory in `Display`/`Debug` impls (`write!(f, …)`, never `f.write_str(&format!(…))`) and worthwhile in loops that append to a reused buffer (PERF-11). Requires `use std::fmt::Write` (for `String`) or `std::io::Write` (for streams/files); the two traits collide if both are in scope, so alias one. Notes: (1) `write!` to a `String` cannot actually fail — `.unwrap()` there is idiomatic, not a lurking panic; (2) writing to a raw `File`/`TcpStream` issues a syscall per `write!`, so wrap it in `BufWriter`; (3) `format_args!` is only useful for *forwarding* formatting through a custom API (`fn log(args: fmt::Arguments)`) — calling `buf.write_fmt(format_args!(…))` directly buys nothing over `write!`, which expands to exactly that, and the `Arguments` value borrows its temporaries so it cannot be stored in a `let` binding
- **PERF-14.** Mark rarely-taken paths `#[cold]` so the optimizer keeps them out of the hot path's instruction cache and stops inlining them into it. The payoff comes from *extracting* the cold work into its own function and marking that — `#[cold]` on a function that is still called on the common path does nothing useful. Typical targets: error-construction helpers (`fn parse_failed(input: &str) -> Error`), retry/fallback branches, and slow-path re-initialization. Pair with `#[inline(never)]` when the function is small enough that LLVM would inline it anyway. Two caveats that bound the value: (1) rustc already treats panicking and `Err`-returning paths as cold in most cases, so an explicit `#[cold]` on an ordinary `?` path usually changes nothing measurable; (2) it is a hint, and misapplying it to a path that turns out to be hot is a pessimization. Treat it as a targeted fix after profiling shows i-cache pressure or a bloated hot function (PERF-6), not as a default annotation
- **PERF-15.** `String` is the right default; reach for small-string optimization only where the workload is dominated by short, numerous strings — parser tokens, map keys, identifiers, symbol tables, metric and field names, route segments, enum-like protocol values, config normalization, anything held as a large in-memory collection of short textual values. `compact_str::CompactString` is the same size as `String`, stores up to 24 bytes inline (12 on 32-bit) and spills to the heap beyond that, and is close to a drop-in replacement — it removes the per-value allocation without inventing a private string type in the codebase. Preconditions, in order: (1) profile first (PERF-6) — this is the string analogue of PERF-9 and pays off for the same reason, not by default; (2) check first whether the values could simply be `&str` borrowed from the source buffer (PATTERN-3), which costs nothing at all, or `Box<str>`/`Arc<str>` if they are immutable after construction and only the `String` capacity word is being wasted. Crate MSRV is 1.71
- **PERF-16.** A cache is not a `HashMap` plus a cleanup task. An ad-hoc map used as a cache typically ships with no eviction policy, no size cap, no expiry, and no answer for concurrent misses — so it grows without bound (a memory-exhaustion path whenever keys are attacker-influenced, SEC-33), serves stale entries indefinitely, and stampedes when many tasks miss the same key at once. Prefer `moka` (`moka::sync::Cache`, `moka::future::Cache`) over hand-rolling: size- and weight-based eviction, TTL/TTI expiry, concurrent access without a global lock (CONC-7), and per-key atomic insertion through `get_with`, which coalesces concurrent loads of the same key and is the actual fix for stampede. Note `moka` ≥ 0.12 no longer spawns background threads — maintenance runs on caller threads. The crate owns the mechanics; the review owns the policy: every cache must have a stated key, value, maximum size, TTL, and invalidation expectation, and a cache with no answer for those is the finding regardless of implementation. Fits derived values that are expensive to recompute but not worth persisting — resolver lookups, token introspection results, compiled templates, metadata reads, short-TTL authorization decisions. Weigh the cost: a cache changes system behaviour, can mask consistency bugs, and complicates debugging
- **PERF-17.** Do not reach for `Arc` (or `Box`) reflexively on nested types — each layer is a pointer to chase, and on a hot path a two-deep `self.config.feature.is_enabled()` is two dependent DRAM round-trips to read one bool. This is the most common shape in code ported from a language where every object is a reference (ARCH-13). Shared ownership is worth its indirection when the value is genuinely large, genuinely shared by several owners, and genuinely outlives its creator; short of that, embed the data. Where a deep field is read far more often than the structure changes, **lift it**: copy the hot `bool`/`u32` up into the outer struct so the common path touches one cache line, and keep the `Arc` for the cold, whole-object access. Trade-off: a lifted field is a copy that must be kept in sync — do it for values that change rarely or never, not for live state, and confirm the win by profiling (PERF-6)
- **PERF-18.** Store immutable owned sequences as `Box<[T]>` / `Box<str>` / `Arc<str>` rather than `Vec<T>` / `String`. A growable collection is a `(ptr, len, capacity)` triple; converting it (`vec.into_boxed_slice()`, `string.into_boxed_str()`) shrinks to fit and drops the capacity word, cutting the handle from 24 bytes to 16 on 64-bit and fitting a third more of them into cache. Worth doing when the sequence is (1) instantiated in large numbers, (2) never resized after construction, and (3) internal — a public API returning `Box<[T]>` pushes an unfamiliar type onto callers for no gain (API-18), so convert at the storage boundary and hand out `&[T]`/`&str`. `Arc<str>` additionally replaces `Arc<String>`, which is a pointer to a pointer for no reason. See PERF-15 for the complementary case (many *short* strings, where the win is inline storage rather than a dropped capacity word)
- **PERF-19.** Telemetry on a hot path must be cheap enough to leave permanently enabled. A library's logs and metrics are not opt-in from the operator's perspective — they will be on, under load — so an event emitted per item in an inner loop is a per-item allocation and a per-item formatting cost that the caller cannot remove. Keep inner loops free of emission entirely where possible; where it is unavoidable, emit structured fields rather than a formatted string (READ-12 — `event!(…, message.id = m.id(), "…")` allocates nothing until something renders it, `log(format!("Emitting message {}", m.id()))` allocates every iteration). Best of all is to move the event up a level and let the reader reconstruct the detail offline: one "processing batch" event carrying the batch id beats N per-message events. Note this is about *volume and cost*, not about level — a `debug!` in a hot loop still evaluates its arguments' formatting machinery at the callsite
- **PERF-20.** Call `shrink_to_fit()` on large, long-lived collections built by growth. `Vec`, `String`, and friends grow by doubling, so a collection filled by `push` in a loop ends up holding as much as ~2× the memory it needs, and if the value is then stored for the lifetime of the process that overhead is permanent. Applies to caches, loaded indexes, parsed documents, and interned tables — not to short-lived locals, where the call is a pointless copy. Prefer sizing up front (PERF-2) and use `shrink_to_fit` where the final size could not be known; it is redundant after `into_boxed_slice`/`into_boxed_str` (PERF-18), which already shrink
- **PERF-21.** Two build-level knobs apply to **applications** (they are ignored for libraries, which do not control the final build) and are worth setting deliberately once rather than chasing in code. **Global allocator:** the system allocator is often the bottleneck in allocation-heavy services; swapping in `mimalloc` or `jemalloc` (`#[global_allocator] static GLOBAL: MiMalloc = MiMalloc;`) is a few lines and commonly buys a double-digit percentage on allocation-heavy benchmarks. It is not free — binary size, an extra dependency, and platform caveats (musl, unusual targets) — so measure it on your own workload (PERF-6) rather than adopting it on reputation, and prefer removing the allocations first (PERF-2, PERF-11, PERF-15). **`target-cpu`:** the default build targets the generic baseline for the architecture, so nothing newer than SSE2 is used on x86-64. A server binary deployed to a fleet whose ISA you control can raise it in `.cargo/config.toml` (`[target.x86_64-unknown-linux-gnu] rustflags = ["-C", "target-cpu=x86-64-v3"]`). The hazard is that the resulting binary **crashes with SIGILL** on any host below that level, so it must match the *guaranteed* floor of the deployment target, not the developer's laptop — and it is the wrong tool for anything redistributable. **The `[profile.release]` defaults are a compile-time/run-time compromise, not a shipping configuration**, and are worth revisiting once for a binary that is built rarely and run constantly: `lto = "fat"` (or `"thin"` for most of the benefit at a fraction of the build cost) lets the optimizer inline and devirtualize across crate boundaries — which is also what makes `#[inline]` unnecessary on cross-crate hot functions (PERF-5) — `codegen-units = 1` removes the parallelism-induced optimization barriers within a crate, and `strip = "symbols"` shrinks the artifact (keep `debug = 1` instead where the binary is profiled or symbolicated in production). Expect a substantially slower release build in exchange, so apply it to the release profile and not to the one developers iterate on, and measure the result (PERF-6) rather than assuming it.
