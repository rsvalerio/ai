# MACRO rules

## Macros (typical severity: Low--Medium)

- **MACRO-1.** A macro is what you write when you have run out of language, and Rust gives you a lot of language — so a macro needs a reason that traits, generics, or a plain function could not satisfy (TRAIT-8). Macros are opaque to readers and to `rustdoc`, inflate compile times in projects that otherwise use none, produce error messages pointing into generated code, and can break at edition boundaries where syntax and semantics shift. The counterintuitive part: **the more structurally complex the expansion, the worse a fit a macro is**. The macro that earns its keep makes the reader think "I know exactly what this generates, I just don't want to type it" — a newtype-plus-impls, a table of test cases, a `From` cascade. When one *is* warranted, prefer a declarative `macro_rules!` over a proc macro: expansions can be read with `cargo expand`, there is no `syn`/`quote` build-time cost, and the failure modes are far shallower. Reach for a proc macro only for what `macro_rules!` genuinely cannot do — inspecting a type's fields (`#[derive]`), or rewriting an item body
- **MACRO-2.** A macro must not lie about what it expands to. Macros can rewrite tokens arbitrarily; that they *can* turn a struct into an enum, add a parameter to a function, or make a sync `fn` `async` is precisely why they must not — the reader is left with source that does not describe the program. Flag any macro that changes an item's kind, alters a function's visible signature or arity, or flips its `async`-ness. The related trap is **implied items**: a macro that defines extra types the user never wrote (`#[my_macro] struct UserType;` also emitting `struct ExtraType;`) collides with the user's own names, collides with a second invocation of itself, is invisible in source, and is forgotten when someone re-exports the module. The one accepted exception is the namespace overload popularized by Rocket and `axum` — emitting a `struct foo` alongside `fn foo`, which Rust's separate value/type namespaces allow and casing conventions keep from clashing — and even that is for internal handler registration, not for a type users must name
- **MACRO-3.** Structure macro crates so they are testable and so their expansions resolve. Three conventions, each a finding when missing: (1) **the expansion must not assume the caller's dependencies.** Emitting `impl ::bar::Bar for T` breaks unless the user happens to depend on `bar` under that exact name; re-export what the expansion needs from a `#[doc(hidden)] pub mod _private { pub use ::bar::Bar; }` in your own crate and emit `::foo::_private::Bar`. (Such a module is a deliberate exception to API-13's single-path rule.) Correspondingly, a proc macro may assume it is used *through* its main crate and emit paths for that — supporting invocation from the internal split crates, or under a renamed import, is complexity for a UX gain the ecosystem does not expect. (2) **A proc-macro crate cannot invoke the macro it defines.** It can still hold ordinary `#[cfg(test)]` tests over plain helper functions — the restriction is on expansion, not on testing — but nothing inside it can expand its own macro, so every *expansion* test needs a separate crate: `tests/`, a fixture crate, or `trybuild`. A crate whose macro logic is exercised nowhere is the finding. The conventional way to avoid that is to keep `foo_proc` a one-line shim (`foo_proc_impl::my_macro(attr.into(), item.into()).into()`) over an ordinary library crate `foo_proc_impl` that transforms `proc_macro2::TokenStream`, which puts the whole transformation under plain unit tests — snapshot tests (`insta`, TEST-30) over the generated tokens read well here. The split is a testability design, not a language requirement; an equivalent arrangement that gets the logic covered is fine. (3) Add `trybuild` UI tests for the *negative* cases, so the error a user gets from a malformed invocation is itself covered; `compile_error!` with a readable message is the right way to reject one (ARCH-12)
