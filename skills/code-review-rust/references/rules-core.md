# Core Rust Rules

## Ownership & Borrowing (typical severity: Medium--High)

- **OWN-1.** Prefer `&T` over `&mut T`; smallest scope possible
- **OWN-2.** *Retired.* Do not reuse this ID for new rules; old findings may reference it.
- **OWN-3.** Return owned data to avoid lifetime leakage
- **OWN-4.** `Cow<T>` for conditional ownership
- **OWN-5.** *Retired.* Do not reuse this ID for new rules; old findings may reference it.
- **OWN-6.** Prefer `Option<&T>` over `&Option<T>`
- **OWN-7.** `AsRef`/`Borrow` to accept owned or borrowed
- **OWN-8.** If you're cloning to satisfy the borrow checker, rethink ownership design — mechanical detection of redundant clones is handled by `clippy::redundant_clone`; this rule covers the design smell of cloning as a workaround for lifetime issues
- **OWN-9.** `Rc` for single-thread sharing; `Arc` when crossing thread boundaries; `Weak<T>` to break cycles. For shared-state primitive selection (`Arc<Mutex<T>>` vs `Arc<RwLock<T>>` etc.), see CONC-1
- **OWN-10.** `RefCell<T>` for single-thread interior mutability only; enforces borrowing rules at runtime (panics on violation). For cross-thread sharing, see CONC-1; for the security angle of `unsafe impl Sync` with `RefCell`, see SEC-24
- **OWN-11.** Deref early in chains to reduce `&` noise (e.g., `let val = *wrapper;` before chaining methods instead of `(&wrapper).method()`)
- **OWN-12.** Implement `Deref` only for transparent wrappers and smart pointers; never use it to simulate OOP inheritance — implicit method resolution through deref coercion creates confusing APIs and hides ownership semantics

## Error Handling (typical severity: High)

- **ERR-1.** Propagate with `?`; handle or propagate, never both; similarly, log at the handling site only — propagating an error and also logging it creates duplicate log entries
- **ERR-2.** Define domain error enums; document which variants each public function may return and under what conditions. For organizing error types (inline vs. `error.rs`), see ARCH-8
- **ERR-3.** Choose error crates by caller intent: `thiserror` when callers match on variants, `anyhow` when callers just propagate/log; combine both (thiserror for types, anyhow for context) when needed. A third case sits outside that axis: when the error must point *into* a document the user wrote — config file, DSL, template, query, migration, generated source — `miette` layers source snippets, labelled spans, related spans, and suggestions on top of a `thiserror`-style type via `#[derive(Diagnostic)]`, turning "unexpected token" into a report that names the offending region and what would have been accepted. Keep it at the *human* boundary: developer tools, compilers, linters, formatters, generators, config-heavy CLIs. Service errors headed for logs and observability should stay structured (READ-8); routing every internal error through a terminal-pretty-printing layer costs a dependency and an abstraction with no reader on the other end
- **ERR-4.** Add context with `.with_context()`
- **ERR-5.** Detection of `unwrap`/`expect` in production code is handled by `clippy::unwrap_used` (restriction lint). This rule's unique value is severity nuance: downgrade to Low on provably infallible paths (constant `Regex::new`, known-literal parse, `Result<T, Infallible>`). Prefer `expect("reason")` even then. Note: `if x.is_some() { x.unwrap() }` is not valid — use `if let`.
  **Scanning guidance:** `unwrap()` / `expect()` inside `#[cfg(test)]` modules, `#[test]`-attributed functions, `tests/` directories, `#[cfg(any(test, ...))]` blocks, or `test-support`-feature-gated code is **not** a finding — test panics are the explicit failure mechanism. Only count occurrences in production code paths. Before filing an ERR-5 finding, confirm the callsite is reachable outside `#[cfg(test)]`. Absolute counts that ignore this filter are meaningless (in this workspace a naive scan found 371 unwraps, all in tests; the real production count was zero).
- **ERR-6.** `Result<Option<T>>` over sentinel values
- **ERR-7.** Map internal errors to public types at module boundaries; use `map_err()` for simple conversions and `.context()`/`.with_context()` (anyhow) for adding caller-relevant context — this hides implementation details and keeps internal error types private
- **ERR-8.** `unwrap_or_else` for defaults
- **ERR-9.** Implement `Error::source()` for error chains — `thiserror`'s `#[from]` and `#[source]` wire it up for you. **Do not then interpolate the source into the `#[error(...)]` message.** `#[error("Request failed: {0}")] Request(#[from] reqwest::Error)` sets both the message *and* the source to the same value, so every chain-walking printer says it twice: `anyhow`'s `{:#}` renders `Request failed: connection refused: connection refused`, and its `{:?}` renders the message followed by a `Caused by:` block repeating it. (Verified on thiserror 2.0 / anyhow 1.0.) The variant's message should say what *this* layer was doing — `#[error("request to the upstream API failed")]` — and let the chain supply the cause. Interpolating a field is correct for data the source does not carry (`#[error("unknown field `{field}`")]`); it is wrong for the source itself. Flag any `#[error]` whose format argument is the same field marked `#[from]`/`#[source]`
- **ERR-10.** Never use `Result<T, String>` — use proper error types
- **ERR-11.** Panic for bugs, `Result` for expected failure. Panicking macros (`assert!`, `unreachable!`, `panic!`) are for violated *internal* invariants — conditions that are unreachable unless the code itself is wrong. Invalid *external* input (user data, config, network payloads, public-API arguments) must return `Result`; asserting on it converts an expected failure into a crash and conflicts with ERR-2/ERR-10. Specifically:
  - `assert!(cond, "reason")` — internal invariants only; always give the message a reason.
  - `unreachable!("why")` — impossible match arms and state-machine transitions. Prefer making the state unrepresentable (PATTERN-1 typestate, or a narrower enum) over documenting it as unreachable. Never place `unreachable!` on a path reachable from untrusted input — that is a remote panic (see SEC-33).
  - `todo!()` / `unimplemented!()` — `todo!` for planned-but-unfinished work, `unimplemented!` for deliberately unsupported cases. Either one reachable from a shipped code path is a panic bomb; flag any occurrence outside prototypes and stub trait methods that callers provably never invoke.
  For the release-build caveat on `debug_assert!`, see UNSAFE-9.
- **ERR-12.** Attribute panics and errors to the *caller* with `#[track_caller]` (stable since Rust 1.46) rather than embedding `file!()`/`line!()`/`module_path!()` by hand. On a helper that panics or constructs an error, `#[track_caller]` makes the reported location the callsite, and `std::panic::Location::caller()` gives programmatic access. Manual `file!()`/`line!()` capture is only appropriate inside macro definitions; in ordinary logging it is redundant — `tracing` records the callsite on every event automatically (READ-8)
- **ERR-13.** Filesystem errors must name the path. `std::fs` returns a bare `io::Error` — "No such file or directory", with no indication of *which* file — which is useless in a CI log, a container, or a user bug report. Two fixes: attach `.with_context(|| format!("reading {}", path.display()))` at the callsite (ERR-4), or swap the module for `fs_err`, a drop-in `std::fs` mirror (`fs_err::read_to_string`, `fs_err::File`, `fs_err::OpenOptions`) that folds the path into the error automatically. Prefer the second where filesystem calls are scattered — config loading, template rendering, cache reads, artifact writes, migrations, fixture loading — because context that must be remembered at every callsite eventually is not. `fs_err::tokio` (behind the crate's `tokio` feature) mirrors `tokio::fs`, so adopting it does not push async code back onto blocking I/O (CONC-5). Flag any `?` on a `std::fs` call whose error can reach a log or a user without the path attached
- **ERR-14.** Deserialization failures on human-edited input must name the failing field. serde's default message — "invalid type: string, expected u64" — carries no path, so on a nested document the editor cannot find the offending line. Wrap the deserializer in `serde_path_to_error::deserialize`, which exposes `err.path()` (`services[2].timeout_ms`) alongside `err.inner()`. Applies wherever a human authors the document and to any serde data format (JSON, YAML, TOML): service configs, deployment manifests, policy files, workflow definitions, code-generation inputs, test fixtures. Scope: this is a diagnostics improvement only — it does not validate the schema, so SEC-11 still owns size/depth limits and unknown-field rejection; and the field path is for the operator editing the file, not for an untrusted caller (SEC-21)

## Traits & Generics (typical severity: Low--Medium)

- **TRAIT-1.** `From`/`Into` for conversions
- **TRAIT-2.** `impl Trait` in return position for flexibility; in 2024 edition, all lifetimes are captured by default (use `+ use<>` to opt out)
- **TRAIT-3.** Complex bounds → `where` clauses
- **TRAIT-4.** Derive deliberately, not reflexively. `Debug` is usually safe and helpful (except on secret-bearing types — see SEC-5); `Clone`, `Copy`, `Hash`, `PartialEq`/`Eq` are semantic commitments and part of your public API — once derived, removing is a breaking change. Derive only when the type semantically supports the trait and callers need it. `clippy::missing_debug_implementations` partially covers `Debug`; this rule's unique value is the "derive with intent" philosophy (see OWN-8, PERF-3 for clone-usage guidance and SEC-5 for secret types)
- **TRAIT-5.** Blanket impls sparingly (coherence conflicts)
- **TRAIT-6.** Separate read/write traits (ISP)
- **TRAIT-7.** `dyn Trait` only when dynamic dispatch needed
- **TRAIT-8.** Prefer traits over macros (better errors, IDE support)
- **TRAIT-9.** Extract traits when needed for multiple implementations, stable public APIs, or test doubles; start concrete until then. For module boundary design, see ARCH-2
- **TRAIT-10.** Use Generic Associated Types (GATs, stable since Rust 1.65) when an associated type needs to borrow from `&self` or carry a lifetime — e.g., a streaming-iterator-style `trait LendingIterator { type Item<'a> where Self: 'a; }`. Do not adopt GATs pre-emptively; they are a powerful tool for lending-iterator and allocator-like APIs but carry steeper error messages and inference costs than plain associated types
- **TRAIT-11.** On traits whose bounds are commonly unsatisfied, attach `#[diagnostic::on_unimplemented(message = "…", note = "…", label = "…")]` (stable since Rust 1.78 — **no feature gate**, contrary to older write-ups) so the compiler explains *why* a type does not qualify and what to do about it, instead of emitting a bare `the trait bound X: Y is not satisfied`. Placeholders `{Self}`, `{Trait}`, and the trait's generic parameters interpolate into the message. It changes diagnostics only — trait resolution is unaffected — so it is never a correctness fix, only an ergonomics one; reserve it for traits with non-obvious requirements (sealed traits per API-8, traits with blanket impls that "should" apply, marker traits gating a builder step). The `diagnostic` namespace is best-effort by design: unknown options and malformed values are lint warnings rather than errors, so a typo silently does nothing — confirm the message actually renders. See also `#[diagnostic::do_not_recommend]` (stable since Rust 1.85), which stops the compiler from suggesting an impl that could never apply

## Concurrency (typical severity: High--Critical)

- **CONC-1.** Choose the right shared ownership primitive: `Arc<T>` for immutable shared state; `Arc<RwLock<T>>` when reads dominate and writes are rare; `Arc<Mutex<T>>` for occasional writes; almost never `Mutex<Arc<T>>` (rare exception: atomically swapping the inner `Arc`). **Read-mostly *whole-value* state is a distinct case** worth separating out: config snapshots, routing tables, feature flags, allowlists, certificate bundles — read on nearly every request, replaced wholesale and rarely. `Arc<RwLock<T>>` makes every reader participate in locking for data that almost never changes; `arc_swap::ArcSwap<T>` gives lock-free reads (`.load()` hands back a guard to the current `Arc`) while writers publish a new version with `.store(Arc::new(next))`. The trade-off is that an update *replaces* the value rather than mutating it in place — which is exactly right for configuration (immutable snapshots, atomic publication, no half-updated state) and wrong for state that must be edited field-by-field. In async code that also needs *change notification*, prefer `tokio::sync::watch` (CONC-8): it covers latest-value broadcast and lets receivers await updates. Reach for `ArcSwap` when readers only ever sample the current value, including from sync code
- **CONC-2.** Hold locks briefly; never across `.await`
- **CONC-3.** Prefer channels over shared state; bounded channels provide natural backpressure. Capacity sizing has no universal constant — it is a function of the producer/consumer rate gap and the acceptable queueing latency. Default to a small capacity (4--32) and tune from telemetry (observed queue depth, producer wait time, end-to-end latency). Red flag: unbounded channels in production — they defer OOM to runtime instead of surfacing backpressure
- **CONC-4.** `tokio::select!` for cancellation/timeouts; common patterns: (1) shutdown signal: `tokio::select! { _ = shutdown.recv() => break, msg = rx.recv() => handle(msg) }`, (2) timeout: `tokio::select! { result = work() => result, _ = tokio::time::sleep(dur) => Err(Timeout) }`
- **CONC-5.** Never block in async — common offenders and their async equivalents: `std::thread::sleep` → `tokio::time::sleep`, `std::fs::{read,write,rename,remove_file,create_dir_all,File::create,metadata,exists}` → `tokio::fs::*`, `std::net::TcpStream` → `tokio::net::TcpStream`, synchronous `reqwest::blocking` → `reqwest` async client; for unavoidable blocking (e.g., CPU-heavy compute, blocking C library, sync sqlite/rusqlite calls), use `spawn_blocking` (ASYNC-1). **Checklist for `cli::commands::bench` and `bench::runner`: any `std::fs::*` or sync store call inside an `async fn` is a defect** — either swap to `tokio::fs` or move the block under `tokio::task::spawn_blocking`
- **CONC-6.** Structured concurrency: `JoinSet` for task groups — ensures all spawned tasks are tracked, awaited, and cleaned up; prevents orphaned tasks that silently leak resources or panic. Drop a `JoinSet` to cancel all tasks in the group. Prefer `JoinSet` over ad-hoc `Vec<JoinHandle>` + `join_all` for dynamic task groups
- **CONC-7.** Avoid `Mutex` around collections (`HashMap`, `VecDeque`, `Vec`) in hot paths; prefer `DashMap` (sharded `RwLock`s), `crossbeam::queue`, or manual sharding for high-contention scenarios; for simple patterns, evaluate `std::sync::mpsc` (reworked in Rust 1.67 to be crossbeam-based) before pulling in external crates
- **CONC-8.** Channel type selection:

  | Channel | Context | Use case |
  |---|---|---|
  | `crossbeam::channel` | Sync | Select, bounded with backpressure, multi-producer |
  | `tokio::sync::mpsc` | Async | Point-to-point message passing |
  | `tokio::sync::broadcast` | Async | Fan-out / pub-sub (multiple receivers) |
  | `tokio::sync::oneshot` | Async | Single request-response or completion signal |
  | `tokio::sync::watch` | Async | Latest-value broadcast (config updates, state) |

  Rule of thumb: `crossbeam` for sync code needing `select!` or bounded backpressure; `tokio::sync` for async code — it integrates with the runtime. Backpressure, though, is a property of the *individual* channel, not of the crate: bounded `crossbeam::channel` provides it on the sync side, and among the tokio async channels **only bounded `mpsc::channel(n)` does**. Pick deliberately: **bounded `mpsc::channel(n)`** applies real backpressure, because `send().await` parks the producer once the buffer is full; **`mpsc::unbounded_channel()`** has a non-async `send` that never waits for capacity, so it applies none and grows until memory runs out (CONC-3 — this is the unbounded-queue red flag, and reaching for it to "fix" a slow consumer converts backpressure into an OOM). Note that "never waits" is not "never fails": unbounded `send` still returns `Result<(), SendError<T>>` and errors once every receiver is dropped or closed (verified), so the value is handed back exactly as with the bounded sender — what it never does is *slow the producer down*. **`broadcast::channel(n)`** is a bounded **ring buffer** that does not block the sender at all — when a receiver falls behind, the oldest messages are overwritten and that receiver is told after the fact via `Lagged(n)` (see below). `BroadcastStream` inherits exactly this: wrapping it in a `Stream` does not add backpressure (ASYNC-13). So bounded `mpsc` slows the producer down, `broadcast` drops data instead, and unbounded `mpsc` does neither.

  **Failure shapes differ per channel, and only one of them is "the receiver went away".** Do not write generic "sends and receives can fail, handle them" code — check the actual signature:

  | Operation | Returns | Failure means |
  |---|---|---|
  | `mpsc::Sender::send` | `Result<(), SendError<T>>` | the receiver is gone — either dropped **or still alive but explicitly closed** via `Receiver::close()`. **The unsent value is returned inside the error** (`e.0`), so it can be re-routed, persisted, or counted rather than dropped |
  | `mpsc::Receiver::recv` | `Option<T>` — **not** a `Result` | `None` = no more messages will arrive and the buffer is drained: either every sender dropped, **or the receiver called `close()`**, which stops new sends while still yielding what is already buffered. Normal termination either way, and `while let Some(x) = rx.recv().await` handles it |
  | `oneshot::Receiver` (awaited) | `Result<T, RecvError>` | the sender was dropped without sending — usually a task that panicked or returned early |
  | `broadcast::Receiver::recv` | `Result<T, RecvError>` | `Closed` = all senders gone; **`Lagged(n)` = this receiver fell `n` messages behind and those messages are gone** |
  | `watch::Receiver::changed` | `Result<(), RecvError>` | sender dropped; note `watch` conflates intermediate updates by design — only the latest value is observable |

  `broadcast::error::RecvError::Lagged(n)` is the dangerous one: it is **silent data loss reported as an error**, and `recv()` resumes from the oldest retained message afterwards rather than failing permanently (verified: capacity 4, 10 sends, first `recv()` returns `Lagged(6)` then yields message 6). Code that `?`s it away, or logs it and continues, has just dropped `n` messages from an audit trail, a replication feed, or a cache-invalidation stream while reporting healthy. Flag any `broadcast` consumer that does not treat `Lagged` distinctly from `Closed` — the correct responses are to increase capacity, resynchronize from the source of truth, or fail the consumer loudly, and `n` should be a metric
- **CONC-9.** Understand lock-free trade-offs: CAS retry loops can spin under high contention (many threads competing on the same atomic variable), wasting CPU cycles and potentially performing worse than a `Mutex` under sustained contention; profile with realistic concurrency levels before assuming lock-free is faster — measure both throughput and tail latency
- **CONC-10.** For lazily-initialized global/static state, prefer `std::sync::OnceLock<T>` (stable since 1.70) and `std::sync::LazyLock<T>` (stable since 1.80) over the `once_cell` crate and the legacy `lazy_static!` macro. `OnceLock` for manual initialization, `LazyLock` for closure-based initialization. `once_cell`/`lazy_static` remain acceptable for MSRV <1.80 only — for new code at modern MSRVs, flag as an EFF finding
- **CONC-11.** `thread_local!` for genuinely per-thread state (scratch buffers, per-thread RNG, sync-code context) — each thread gets an independent instance, so no lock is needed. Use the `const { }` initializer (stable since Rust 1.59) when the initial value is const-evaluable: `thread_local! { static BUF: RefCell<Vec<u8>> = const { RefCell::new(Vec::new()) }; }` — it skips the lazy-init check on every access. **Async footgun (flag as a defect):** a tokio task is not pinned to a worker thread — it can resume on a different thread after any `.await`, so a `thread_local!` read before an `.await` and after it may hit different values. Never use `thread_local!` to carry per-*task* context in async code; use `tracing::Span`, `tokio::task_local!`, or an explicit context parameter instead. Also note `thread_local!` destructors do not run for threads that are never joined (including the process exit path), so do not rely on them for flushing or cleanup
- **CONC-12.** Pad independently-written shared state to a cache line with `#[repr(align(N))]` (stable since Rust 1.25) to avoid **false sharing** — two atomics or counters that live in one cache line force the cores writing them to bounce that line back and forth, so throughput collapses even though the values are logically unrelated. The classic shape is a per-worker stats array: `struct Counters([AtomicU64; N])` where every worker hammers its own index and all of them share a line. Prefer `crossbeam_utils::CachePadded<T>` over hand-rolled alignment — it already encodes the per-architecture line size, which is **not** universally 64 bytes (128 on x86-64 and aarch64 because of adjacent-line prefetch, 32 on some embedded targets); a hardcoded `align(64)` is wrong on exactly the platforms where the problem is worst. Costs memory proportional to the padding, so apply it to hot per-worker state, not to every struct with an atomic in it, and confirm with a profiler that the line is actually contended. Alignment beyond this — SIMD operands, DMA buffers, hardware-mandated layout — is a low-level concern outside these rules
- **CONC-13.** A spawned task's failure does not reach anyone unless something joins it. **This rule describes the default `panic = "unwind"` strategy**; under `panic = "abort"` (set in a `[profile.*]`, common in embedded and size-tuned release builds) there is no unwind to catch, so the first panic in any task takes the whole process down immediately — verified: with `panic = "abort"` the `JoinHandle` is never resolved and no line after `h.await` runs, whereas the same binary under unwind reports `is_panic=true` and exits 0. Check the profile before relying on either behaviour; abort turns every task panic into a crash, which is louder but removes the option to supervise.

  Under unwind, `tokio::spawn` catches the unwind and stores the outcome in the `JoinHandle`; drop the handle (or never await it) and the task's panic disappears from the program's control flow. It is not *silent* — the default panic hook still writes `thread 'tokio-rt-worker' panicked at …` to stderr — but nothing else happens: the runtime keeps going, the supervising task never learns the work stopped, and **the process still exits 0** (verified on tokio 1.53). A background flusher, reconciler, or metrics exporter that dies this way leaves a service that looks healthy and has silently stopped doing one of its jobs. Await the handle, or hold tasks in a `JoinSet` (CONC-6) and drain `join_next()`. When you do handle the error, `JoinError` is **not** synonymous with panic — the common `eprintln!("Task panicked: {e:?}")` handler mislabels every cancellation:
  - `e.is_panic()` — the task panicked; `e.into_panic()` returns the payload and lets you `std::panic::resume_unwind` to propagate the failure into the parent.
  - `e.is_cancelled()` — the task was `abort()`ed or its `JoinSet` was dropped. During shutdown this is the expected path and must not be logged as an error (CONC-14).

  Detached tasks are legitimate for genuinely fire-and-forget work, but the choice must be deliberate: if the task's failure would matter to anyone, it needs a supervisor — a `JoinSet`, a restart loop, or at minimum a `tokio::spawn(async move { if let Err(e) = handle.await { … } })` that turns the `JoinError` into a metric and a structured log (READ-8). Setting a process-wide `std::panic::set_hook` that aborts is the blunt alternative when any task panic should take the service down; do it deliberately, not as a substitute for supervision
- **CONC-14.** Graceful shutdown means the signals the platform actually sends. `tokio::signal::ctrl_c()` alone listens for **SIGINT only**; a container runtime, Kubernetes, and systemd all stop a process with **SIGTERM**, whose default disposition is immediate termination — so a service whose shutdown path is `ctrl_c().await` dies instantly on every real deployment restart and runs none of its cleanup. Verified: a process awaiting only `ctrl_c()` and sent SIGTERM exits before the line after the await. Note the SIGKILL that follows in the orchestrator's sequence is *not* what killed it: SIGKILL is sent only if the process is **still alive** when the grace period expires, which is the failure mode of a service that does trap SIGTERM but drains too slowly (see "Bound the drain" below). An untrapped SIGTERM is already fatal on its own. Handle both signals, and on Unix add SIGHUP if the process is not using it for reload:

  ```rust
  use anyhow::{Context, Result};
  use tokio::signal::unix::{signal, Signal, SignalKind};

  /// Install at startup, before serving traffic, so a registration failure is a
  /// startup error with context rather than a surprise during shutdown.
  fn install(kind: SignalKind, what: &'static str) -> Result<Signal> {
      signal(kind).with_context(|| format!("installing {what} handler"))
  }

  async fn shutdown_signal(int: &mut Signal, term: &mut Signal) {
      tokio::select! { _ = int.recv() => {}, _ = term.recv() => {} }
  }

  #[tokio::main]
  async fn main() -> Result<()> {
      // Both fail fast, before anything is served.
      let mut int = install(SignalKind::interrupt(), "SIGINT")?;
      let mut term = install(SignalKind::terminate(), "SIGTERM")?;
      // … start the service …
      shutdown_signal(&mut int, &mut term).await;
      // … cancel, then drain — both handlers are still alive here, so a second
      //     interrupt during the drain is observable rather than swallowed …
      Ok(())
  }
  ```

  **Why the interrupt handler is a long-lived `Signal` and not `tokio::signal::ctrl_c()` inside the `select!`.** Two reasons, and the second is the one that bites. First, `ctrl_c()` returns `io::Result<()>`, so a `select!` arm written `_ = tokio::signal::ctrl_c() => {}` discards a registration error that should have been a startup failure. Second, losing the `select!` race **drops** that future — and tokio's process-wide SIGINT handler stays installed, so SIGINT is thereafter neither delivered to a listener nor fatal. Verified: after a SIGTERM won the race, a SIGINT sent during the drain was silently swallowed and the process drained to completion as if nothing arrived. That is the opposite of what an operator hammering Ctrl-C through a slow shutdown expects. Holding both `Signal` streams in `main` keeps them registered for the whole shutdown, which is what makes "press Ctrl-C again to give up on the drain" implementable at all (verified: the second interrupt is observed). `tokio::signal::ctrl_c()` remains the right portable spelling for the simple case — a one-shot wait that is never raced and never needed again — and on Windows it is the only spelling.

  `tokio::signal::unix` is `cfg(unix)` and needs tokio's `signal` feature; on Windows the counterparts are `signal::windows::{ctrl_c, ctrl_shutdown, ctrl_close}`. Three further requirements, each of which is a separate finding when missing:
  - **Propagate, don't just observe.** Receiving the signal in `main` does nothing for tasks already running. Broadcast it *cooperatively*, so each task reaches its own safe stopping point: `tokio_util::sync::CancellationToken` (`token.cancelled()` in a `select!` arm on every long-lived task) or a `watch::Sender<bool>`. CONC-4 has the `select!` shape. Note `JoinSet::shutdown()` is **not** in this list — it aborts, which is the force-quit step below, not a way to ask tasks to wind down.
  - **Bound the drain.** Wrap the "wait for in-flight work" phase in `tokio::time::timeout`; an unbounded drain converts a graceful shutdown into a hang that the orchestrator resolves with SIGKILL anyway. Size the deadline below the platform's grace period (Kubernetes `terminationGracePeriodSeconds`, default 30s). Only *after* that deadline expires does force-abort apply — `JoinSet::shutdown()` (abort every task and await it) or `handle.abort()` per task — and everything under "Release externals" about what abort skips applies to whatever it catches mid-flight.

    **The force path is not itself bounded, because `spawn_blocking` work cannot be aborted once it has started** (tokio 1.53.1). `abort()` on a running blocking task returns immediately and does nothing: measured, the call took ~1.5µs, the closure ran to completion, and `handle.await` returned **`Ok(value)`** — not even a `JoinError`, so a supervisor checking `is_cancelled()` sees a clean success. `JoinSet::shutdown()` inherits this and simply waits: with one 3s blocking task in the set it took 2.7s to return, versus ~0.5ms to abort an equivalent async task. A force-abort step assumed to be instant therefore blows straight through the drain deadline and into the platform's grace period, which is the SIGKILL the deadline existed to avoid. Keep blocking work off this path entirely: give long `spawn_blocking` closures a cooperative cancellation flag they poll between chunks (an `AtomicBool`, a `CancellationToken` checked with `is_cancelled()`), and bound the runtime teardown separately with `Runtime::shutdown_timeout` so the *wait* ends on a deadline you chose rather than one the orchestrator chose (verified: returned in 1.0005s against a 10s blocking task). Be precise about what that buys, because the name oversells it: **it stops waiting; it does not stop the work.** A `spawn_blocking` closure that has already started is not terminated and its thread is not killed — it is merely no longer awaited, and it keeps running until it returns, still holding whatever it holds and still performing whatever it does. Verified: with the runtime dropped after a 1s `shutdown_timeout`, an abandoned closure went on to complete two seconds later and write its output file. So a connection, lock, temp file, or partial write owned by that closure outlives "shutdown complete", and any side effect it has left to perform will still land — possibly after the code that was supposed to flush and close things has finished. Treat `shutdown_timeout` as a bound on how long you *block*, and cooperative cancellation as the only thing that bounds what actually *runs*. Note it also takes `self`, so it is unavailable under `#[tokio::main]`; what it requires is an *owned* runtime, which either `Runtime::new()` or `runtime::Builder` provides — reach for the builder only when you also need to configure worker threads, names, or timers. Keep that value in `main` so there is something to call `shutdown_timeout` on. Chunk the work finely enough that the poll interval fits inside the drain budget — a closure that checks a flag once every 30s is not cancellable in any way that matters.
  - **Release externals explicitly.** Connection pools, NATS clients (NATS-7 `drain()`), open writers, and in-memory buffers need flushing on this path. Aborting a task *does* run `Drop` — the future is dropped at its current await point, destroying owned locals and task-local values in scope (verified on tokio 1.53) — but `Drop` is synchronous, so it cannot await. Anything whose release is itself an async operation (a NATS `drain()`, a graceful connection close, a final flush that round-trips) will not happen, and neither will any code positioned *after* the await the task was parked on. Cleanup that must be awaited belongs on the shutdown path itself — signal the task, then let it finish — not in a `Drop` impl and not after the await of a task you are about to abort.

  Note what the example does *not* do: `signal()` returns `io::Result<Signal>`, and `.expect()` on it is an ERR-5 finding in a long-running service. Failing to install a SIGTERM handler is worth refusing to start over — but as a propagated startup error carrying context (ERR-4), surfaced before the process accepts traffic, not as a panic buried in a shutdown helper that runs an hour later. Registering at startup rather than at shutdown is the point: a handler installed lazily on the shutdown path can fail at the one moment there is no longer anywhere to report it

## Async (typical severity: Medium--High)

> ASYNC rules assume **tokio** as the async runtime. If the project uses a different runtime (e.g., `async-std`, `smol`), adapt API references accordingly.

- **ASYNC-1.** `spawn_blocking` for CPU-heavy work
- **ASYNC-2.** *Retired.* Channel selection is owned by **CONC-8**. For async-vs-sync `Mutex` choice, use `parking_lot::Mutex` / `std::sync::Mutex` when the critical section is short and never crosses `.await`; reach for `tokio::sync::Mutex` only when you must hold the guard across `.await` (see CONC-2)
- **ASYNC-3.** Bounded channels for backpressure (see also CONC-8 for detailed guidance)
- **ASYNC-4.** Batch small, fast-completing tasks (e.g., individual DB row inserts) into fewer spawned futures to reduce scheduler overhead; do NOT batch operations that should run independently or have different cancellation requirements — batching unrelated work couples their failure modes
- **ASYNC-5.** `join_all`/`FuturesUnordered` over serial `.await` in loops. The same defect appears one level up in stream pipelines: `while let Some(x) = s.next().await { work(x).await }` and `.then(…)` run one item at a time regardless of how many are ready — use `StreamExt::buffered` (ordered), `buffer_unordered` (completion order), or `for_each_concurrent` with an explicit concurrency limit, which doubles as the bound that keeps the fan-out from becoming unbounded (CONC-3, ASYNC-13)
- **ASYNC-6.** Timeouts + retries + exponential backoff for all external calls. Pattern: wrap with `tokio::time::timeout(dur, fut).await` → on timeout, retry with exponential backoff (`delay * 2^attempt`, cap at max). Use `tokio-retry` crate for production retry logic; hand-roll only for simple cases. Always set a max retry count to avoid infinite loops. Two details the shape of the return type makes easy to get wrong:
  - **The result nests.** `timeout(dur, fut)` yields `Result<T, Elapsed>` where `T` is the future's own output, so wrapping a fallible call gives `Result<Result<T, E>, Elapsed>` and needs both layers handled: `Ok(Ok(v))` success, `Ok(Err(e))` the operation failed, `Err(_)` it never finished. Collapsing them with `??` or `.flatten()` is fine *only* if the outer `Elapsed` is first mapped into a domain variant (`#[error("upstream timed out after {0:?}")] Timeout(Duration)`) — a bare `Elapsed` propagated to a caller says "deadline expired" with no indication of which deadline (ERR-2, ERR-4).
  - **A timeout cancels, it does not roll back.** On expiry the inner future is dropped at whatever `.await` it was parked on; anything it had already done — rows written, messages published, files partly rewritten — stays done, and anything after that await never runs. Treat a timed-out external call as *unknown outcome*, not as failure: retrying it must be idempotent (idempotency key, conditional write, dedup on the consumer), and any cleanup that must happen has to live in a `Drop` impl or outside the timed region, not in code that follows the await.
- **ASYNC-7.** Use sync code when async adds no value. Async has overhead (future state machines, polling, context switching). Decision: use async for network I/O, concurrent operations, and event-driven flows; use sync for CPU-bound work (via `spawn_blocking`), simple sequential I/O, and operations that don't benefit from concurrency. An `async fn` that never yields is just overhead
- **ASYNC-8.** Insert `tokio::task::yield_now().await` in compute loops that run for more than ~1--5ms without an `.await` point, to avoid starving other tasks on the runtime; for longer compute (>5ms), prefer `spawn_blocking` (ASYNC-1)
- **ASYNC-9.** Separate state from task logic; pass only what tasks need; minimal tokio architecture
- **ASYNC-10.** Prefer native `async fn` in traits (stable since Rust 1.75) over the `async-trait` crate. When callers need `Send`-bounded futures (common in multi-threaded tokio runtimes), use `#[trait_variant::make(Send)]` from the `trait-variant` crate to generate a `Send`-bounded variant — this preserves static dispatch and avoids the `Box<dyn Future>` allocation that `async-trait` introduces. Reach for `async-trait` only when you genuinely need `dyn Trait` object-safety that `trait-variant` can't yet provide (deeply heterogeneous collections of erased async trait objects)
- **ASYNC-11.** Use async closures `async || {}` with `AsyncFn`/`AsyncFnMut`/`AsyncFnOnce` traits (stable since Rust 1.85); check project MSRV before adopting. The hierarchy mirrors `Fn`/`FnMut`/`FnOnce` (`AsyncFn` ⊃ `AsyncFnMut` ⊃ `AsyncFnOnce`), so accept the least-restrictive bound a callee needs. **`Send` caveat:** the `AsyncFn`-family `Send`-bound story is still incomplete — when the returned future must be `Send` (e.g. `tokio::spawn` on a multi-threaded runtime), prefer an explicit `F: Fn(T) -> Fut, Fut: Future<Output = …> + Send + 'static` signature, or move owned captures into an `async move` block, rather than relying on `AsyncFn` to infer the `Send` bound. `AsyncFn` is the right default for single-threaded use and `Arc`-protected shared state (see also ASYNC-10 for the trait-method `Send` story via `trait_variant`)
- **ASYNC-12.** Prefer `std::pin::pin!` (stable since Rust 1.68) over `Box::pin` when a future only needs to be pinned for the current scope — it pins to the stack frame with no heap allocation. The common case is polling a future repeatedly across loop iterations of `tokio::select!`, which requires `&mut fut` and therefore a pinned future: `let fut = pin!(do_work()); loop { select! { r = &mut fut => …, _ = tick.tick() => … } }`. Reach for `Box::pin` only when the pinned future must outlive the scope or be stored in a struct/collection (`Vec<Pin<Box<dyn Future>>>`)
- **ASYNC-13.** `Stream` is the *asynchronous* `Iterator`, not a push-based inversion of it. Both are **pull**-based: `Iterator::next` returns `Option<Item>` and `Stream::poll_next` returns `Poll<Option<Item>>` — the only difference is that a stream may answer "not yet" (`Poll::Pending`) and register a waker rather than block the thread. The consumer still drives it; nothing is pushed at it. (The genuinely push-shaped counterparts are `Sink`, `tokio::sync::broadcast`, and callback registration — reach for those when the *producer* must drive.) Choose by **readiness, not by finiteness**: iterators can be infinite (`std::iter::repeat`, `successors`, `cycle`) and streams are frequently finite, so the deciding question is only whether producing the next item requires awaiting — sockets, channel receivers, paginated HTTP, `Interval` ticks yes; an in-memory `Vec` no (ASYNC-7). There is still no stable trait in `std` (`std::async_iter::AsyncIterator` is nightly-only as of Rust 1.98), so depend on `futures::Stream` / `tokio_stream`; prefer returning `impl Stream<Item = T>` from library APIs (the async counterpart of API-3) and build it with `async_stream::stream!` instead of hand-writing a `poll_next` state machine. Stream adapters are lazy exactly like iterator adapters — a `.map()` that is never polled to completion does no work (PERF-1). Because the consumer controls polling, a `Stream` *expresses* backpressure — but it only *applies* it when the source honours demand. A stream that produces items on demand (an `AsyncRead`, a paginated HTTP fetcher, `async_stream::stream!` awaiting its own work) genuinely throttles the producer by not being polled. A stream that merely *drains* something already filling up does not: `ReceiverStream` over an `mpsc::unbounded_channel`, a `BroadcastStream`, or any adapter over a buffer someone else writes to will let that buffer grow without limit no matter how slowly it is polled — the bound has to come from the channel (CONC-3, CONC-8), not from the stream in front of it. Check where the items are actually produced before treating a `Stream` as the pull-shaped alternative to an unbounded channel. **Three footguns:** (1) `StreamExt::next` requires `Unpin` — pin with `std::pin::pin!` before looping (ASYNC-12); (2) `futures::StreamExt` and `tokio_stream::StreamExt` are distinct traits with overlapping method names and *different signatures* (`futures`' `fold` takes an async closure, `tokio_stream`'s takes a sync one), so importing both yields ambiguity errors — pick one per module; (3) `futures::StreamExt` has no `sum`/`product` — use `fold`
- **ASYNC-14.** Async I/O does not turn end-of-file into "wait for more data". `tokio::fs::File` behind `BufReader::lines()` — or any `AsyncRead` — reports EOF and ends the loop exactly like its `std::fs` equivalent; `async` means the *thread* is not blocked while a read is in flight, not that the reader follows a file still being appended to. (Measured: a `tokio` line reader over a growing file terminates at the current EOF in ~250µs and never observes later appends.) Implementing `tail -f` requires an explicit strategy — re-poll after a delay on EOF while tracking byte offset and handling truncation and rotation (inode change), watch via `notify` (inotify/kqueue), or subscribe to the log transport rather than the file. Flag any "follow the log" loop that relies on async alone to block at EOF; it will exit on the first quiet moment and silently stop processing. Related trap: `tokio::io::Lines` is **not** a `Stream` — it exposes an inherent `next_line().await` returning `io::Result<Option<String>>`; wrap it in `tokio_stream::wrappers::LinesStream` (requires tokio-stream's `io-util` feature) to get `StreamExt` (ASYNC-13)

## Performance (typical severity: Medium)

- **PERF-1.** Avoid premature `.collect()` — keep data as iterators through chains and collect only at the final consumption point; unnecessary intermediate collections waste allocations and defeat lazy evaluation. Note: basic indexed-loop-to-iterator conversion is handled by `clippy::needless_range_loop`
- **PERF-2.** `Vec::with_capacity()` when size known — eliminates reallocations in hot paths
- **PERF-3.** Avoid `.clone()` in hot paths; use `Option::take()` or `std::mem::replace()` to move instead of copy (see also OWN-8 for general clone guidance)
- **PERF-4.** `Option::take()` for safe resource cleanup; prevents double drops when moving out of `Option`
- **PERF-5.** `#[inline]` exposes a function's body to cross-crate inlining (non-generic functions are otherwise monomorphized in the defining crate only). Within a crate, LLVM inlines across codegen units only with LTO or `codegen-units = 1`; otherwise cross-CGU calls are opaque. Use `#[inline]` on small, hot, cross-crate functions; use `#[inline(always)]` sparingly and only when profiling confirms it. Generic functions and `#[inline]` functions are inlined at the call site by default
- **PERF-6.** Benchmark release builds only — debug builds disable optimizations and produce misleading numbers (5--20x slower). Tools: `cargo criterion` for benchmarks, `cargo flamegraph` for CPU profiling, `tokio-console` for async task diagnostics. Workflow: profile → identify 1--2 dominant hotspots (typically 80% of cycles) → optimize those → measure again; never optimize without profiling first
- **PERF-7.** Prefer pass-by-value for small `Copy` types (≤16 bytes, roughly two machine words) in inner loops — indirection through `&T` adds a load per access and inhibits register allocation. `clippy::trivially_copy_pass_by_ref` and `large_types_passed_by_value` flag the obvious cases; this rule's unique value is the hot-loop judgment: profile before restructuring wide signatures
- **PERF-8.** Fast hashers (`ahash` via `HashMap` from `hashbrown`, `FxHashMap`, `XxHash64`) for internal maps where keys are trusted (not user-supplied); default `SipHash` is collision-resistant and needed for untrusted keys to prevent HashDoS; `ahash` is the most common ecosystem choice (used by `DashMap` and `hashbrown` by default)
- **PERF-9.** `SmallVec` when collections are typically small (stack-allocated up to N, spills to heap); `ArrayVec` for hard upper bounds (compile-time capacity). Sweet spot: 1--4 elements typical; beyond ~8, heap `Vec` is usually better
- **PERF-10.** `rayon::par_iter()` for data parallelism on CPU-bound iterators. Sync code only; for async, use `spawn_blocking` + rayon. Not beneficial for I/O-bound or small workloads
- **PERF-11.** Reuse buffers across loop iterations with `.clear()` instead of re-allocating
- **PERF-12.** Replace linear scans with composed maps (`HashMap<K, BTreeMap<...>>`) for O(1)+O(log n) lookup when data has two-level keys; adds memory overhead — profile to confirm benefit
- **PERF-13.** Build formatted output with `write!`/`writeln!` directly into the destination instead of `format!` + `push_str`/`write_all` — the intermediate `String` is a wasted allocation per call. This is mandatory in `Display`/`Debug` impls (`write!(f, …)`, never `f.write_str(&format!(…))`) and worthwhile in loops that append to a reused buffer (PERF-11). Requires `use std::fmt::Write` (for `String`) or `std::io::Write` (for streams/files); the two traits collide if both are in scope, so alias one. Notes: (1) `write!` to a `String` cannot actually fail — `.unwrap()` there is idiomatic, not a lurking panic; (2) writing to a raw `File`/`TcpStream` issues a syscall per `write!`, so wrap it in `BufWriter`; (3) `format_args!` is only useful for *forwarding* formatting through a custom API (`fn log(args: fmt::Arguments)`) — calling `buf.write_fmt(format_args!(…))` directly buys nothing over `write!`, which expands to exactly that, and the `Arguments` value borrows its temporaries so it cannot be stored in a `let` binding
- **PERF-14.** Mark rarely-taken paths `#[cold]` so the optimizer keeps them out of the hot path's instruction cache and stops inlining them into it. The payoff comes from *extracting* the cold work into its own function and marking that — `#[cold]` on a function that is still called on the common path does nothing useful. Typical targets: error-construction helpers (`fn parse_failed(input: &str) -> Error`), retry/fallback branches, and slow-path re-initialization. Pair with `#[inline(never)]` when the function is small enough that LLVM would inline it anyway. Two caveats that bound the value: (1) rustc already treats panicking and `Err`-returning paths as cold in most cases, so an explicit `#[cold]` on an ordinary `?` path usually changes nothing measurable; (2) it is a hint, and misapplying it to a path that turns out to be hot is a pessimization. Treat it as a targeted fix after profiling shows i-cache pressure or a bloated hot function (PERF-6), not as a default annotation
- **PERF-15.** `String` is the right default; reach for small-string optimization only where the workload is dominated by short, numerous strings — parser tokens, map keys, identifiers, symbol tables, metric and field names, route segments, enum-like protocol values, config normalization, anything held as a large in-memory collection of short textual values. `compact_str::CompactString` is the same size as `String`, stores up to 24 bytes inline (12 on 32-bit) and spills to the heap beyond that, and is close to a drop-in replacement — it removes the per-value allocation without inventing a private string type in the codebase. Preconditions, in order: (1) profile first (PERF-6) — this is the string analogue of PERF-9 and pays off for the same reason, not by default; (2) check first whether the values could simply be `&str` borrowed from the source buffer (PATTERN-3), which costs nothing at all, or `Box<str>`/`Arc<str>` if they are immutable after construction and only the `String` capacity word is being wasted. Crate MSRV is 1.71
- **PERF-16.** A cache is not a `HashMap` plus a cleanup task. An ad-hoc map used as a cache typically ships with no eviction policy, no size cap, no expiry, and no answer for concurrent misses — so it grows without bound (a memory-exhaustion path whenever keys are attacker-influenced, SEC-33), serves stale entries indefinitely, and stampedes when many tasks miss the same key at once. Prefer `moka` (`moka::sync::Cache`, `moka::future::Cache`) over hand-rolling: size- and weight-based eviction, TTL/TTI expiry, concurrent access without a global lock (CONC-7), and per-key atomic insertion through `get_with`, which coalesces concurrent loads of the same key and is the actual fix for stampede. Note `moka` ≥ 0.12 no longer spawns background threads — maintenance runs on caller threads. The crate owns the mechanics; the review owns the policy: every cache must have a stated key, value, maximum size, TTL, and invalidation expectation, and a cache with no answer for those is the finding regardless of implementation. Fits derived values that are expensive to recompute but not worth persisting — resolver lookups, token introspection results, compiled templates, metadata reads, short-TTL authorization decisions. Weigh the cost: a cache changes system behaviour, can mask consistency bugs, and complicates debugging

## Unsafe (typical severity: High--Critical)

- **UNSAFE-1.** Small `unsafe` blocks; document invariants with `// SAFETY:` comments. For performance micro-optimization (e.g., `get_unchecked`), only apply after profiling confirms the bottleneck
- **UNSAFE-2.** `unsafe fn` only if every call requires upholding invariants
- **UNSAFE-3.** Use `std::ptr` utilities over raw arithmetic
- **UNSAFE-4.** Test unsafe code thoroughly
- **UNSAFE-5.** Wrap unsafe in safe public APIs
- **UNSAFE-6.** *Not a finding rule.* `unsafe extern` blocks are enforced by the Rust 2024 edition and migrated by `cargo fix --edition`; documented here for reviewer awareness only.
- **UNSAFE-7.** *Not a finding rule.* `#[unsafe(...)]` attribute syntax is enforced by the Rust 2024 edition and migrated by `cargo fix --edition`; documented here for reviewer awareness only.
- **UNSAFE-8.** `std::env::set_var`/`remove_var` are unsafe in 2024 edition; avoid in async contexts
- **UNSAFE-9.** Never guard an `unsafe` precondition with `debug_assert!` alone. `debug_assert!` compiles to nothing when `debug_assertions` is off — which is the default for `--release` — so a bounds or nullity check that "passes in CI" silently vanishes in the shipped binary, turning a caught bug into UB. Use `assert!` (unconditional) for any condition whose violation causes unsoundness; reserve `debug_assert!` for expensive sanity checks on *safe* internal invariants where the failure mode is a wrong answer, not memory unsafety. Same reasoning applies to security checks — see SEC-31 (fail closed)

## Advanced Patterns (typical severity: Low--Medium)

- **PATTERN-1.** Typestate pattern for state machines
- **PATTERN-2.** Phantom types for zero-cost guarantees
- **PATTERN-3.** `bytes::Bytes` for zero-copy IO; `&str` slices for parsing — prefer `Vec<&str>` over `Vec<String>` when parsed tokens don't outlive the source
- **PATTERN-4.** `MaybeUninit` for uninitialized memory
- **PATTERN-5.** Custom allocators for allocation-heavy workloads; arena allocators (`bumpalo`) for batch operations (parsers, AST builders, ECS); pool allocators for fixed-size types. Requires nightly `allocator_api` or stable crate wrappers
- **PATTERN-6.** Embed static assets that ship with the source using `include_str!` (→ `&'static str`) and `include_bytes!` (→ `&'static [u8]`) instead of reading them at runtime. A missing file becomes a compile error rather than a first-request `io::Error`, the deployment artifact is self-contained (no path resolution relative to CWD or the binary), and there is no runtime I/O or error branch to handle. Fits SQL queries, HTML/SQL migration templates, embedded certificates, small fixtures, and license text. **Do not use for:** anything the operator must change without a rebuild (config, tuning, credentials) — embedding makes it immutable; or large assets, which inflate binary size and compile time. Paths are resolved relative to the *including file*, and Cargo tracks them for rebuilds
- **PATTERN-7.** Prefer compile-time constants over runtime environment lookups for values fixed at build time. `env!("CARGO_PKG_VERSION")` / `env!("CARGO_PKG_NAME")` give `&'static str` usable in `const`; `option_env!("…")` returns `Option<&'static str>` for optional build metadata (`option_env!("GIT_SHA").unwrap_or("dev")`) and yields `None` instead of failing the build. `concat!` composes them into a single literal: `const UA: &str = concat!(env!("CARGO_PKG_NAME"), "/", env!("CARGO_PKG_VERSION"));` — useful for User-Agent strings, log prefixes, and banners. **Two caveats:** (1) Cargo does *not* rebuild when an arbitrary env var changes unless a build script emits `cargo::rerun-if-env-changed=VAR`, so a stale `option_env!` value can silently persist across builds; (2) `TARGET`, `HOST`, `OPT_LEVEL`, and `PROFILE` are set only for *build scripts* — `env!("TARGET")` in ordinary crate source fails to compile; re-export them from `build.rs` via `cargo::rustc-env=` if the crate needs them
- **PATTERN-8.** Know when `cfg!(…)` is not a substitute for `#[cfg(…)]`. `cfg!` evaluates to a `bool` at compile time but leaves *both* branches in the source, so both must type-check on every platform — it cannot gate platform- or feature-specific APIs, imports, or items. Use `#[cfg]` for anything conditionally *compiled* (target-specific syscalls, feature-gated modules, optional dependencies); use `cfg!` only when both branches are universally valid and you want a normal `if` (log verbosity, `if cfg!(debug_assertions)` diagnostics, choosing between two portable code paths). A `cfg!` guarding an API that does not exist on all targets is a build break waiting on the next platform, not a style choice. The third member of the family is `#[cfg_attr(cond, attr, …)]`, which applies *other attributes* conditionally — `#[cfg_attr(feature = "serde", derive(Serialize, Deserialize))]` — and is the fix for the anti-pattern of duplicating a whole item under `#[cfg(feature)]` / `#[cfg(not(feature))]` just to vary one derive. Flag any such duplicated pair; the divergence between the two copies is the bug that eventually ships

## Date & Time (typical severity: Medium--High)

- **TIME-1.** Never hand-roll calendar arithmetic. Month lengths, leap years (`year % 4 == 0` is wrong — the rule is `year % 4 == 0 && (year % 100 != 0 || year % 400 == 0)`, so 1900 is not a leap year and 2000 is), day-of-week, week numbers, epoch↔civil-date conversion, and DST transitions are all encoded in maintained crates and all get written incorrectly by hand. Flag any `days_in_month`/`is_leap_year` helper, any manual `day += 1; if day > 31 { … }` rollover, and any `secs / 86_400` used to derive a date. Crate choice: `chrono` (0.4) is the ecosystem default and what most dependencies already pull in; `jiff` (0.2.x, by the `ripgrep` author — pre-1.0, so expect breaking minor releases) is the modern alternative — a Temporal-inspired API with a bundled tzdb whose zoned types make TIME-3 correct *by default* rather than by remembering to use the right method, and it is the better pick for new code that does real zoned arithmetic; the `time` crate (0.3) is the low-dependency option, but its local-offset support is conditional in three ways at once: `OffsetDateTime::now_local()` exists only under the `local-offset` feature, returns `Result<_, IndeterminateOffset>`, and is backed by a per-target implementation (unix/windows/wasm, with a fallback that always fails elsewhere). It also historically refused outright in multi-threaded programs — the restriction has since been relaxed, so verify the behaviour against the version and target in use rather than either the old reputation or this sentence. It suits UTC-only code best — note it also carries much the highest MSRV of the three (1.88 as of 0.3.55, against 1.62 for `chrono` and 1.70 for `jiff`) and raises it freely between patch releases, so check it against the project's `rust-version` before adopting. Do not mix two of them in one crate — the conversions are lossy at the edges and the `Duration` types collide
- **TIME-2.** Compute, store, compare, and log in UTC (`Utc::now()`); convert to `Local` only at the point of display. `Local::now()` depends on process environment (`TZ`, host tzdb), so the same code renders a different wall-clock string in a container, in CI, and on a developer laptop. Be precise about where the damage actually is, because the obvious version of this rule over-flags: `DateTime<Tz>` compares and orders by the underlying instant, so two `DateTime<Local>` values are comparable whatever zone each was resolved in, and chrono's own `Display` and default serde impls both emit the offset — a plain `println!` or `serde_json` round-trip of a `DateTime<Local>` does not lose the instant. The defect is **offsetless** rendering: `.format("%Y-%m-%d %H:%M:%S")`, `.naive_local()`, and a `TIMESTAMP WITHOUT TIME ZONE` column each drop the anchor, and the value then means a different instant to every reader that assumes a different zone. Two traps survive even when the offset is kept: an offset is not a zone — `+02:00` does not say *which* zone, so no DST-correct arithmetic can be done on it later (persist an IANA name alongside when the value will be recomputed); and anything keyed on the *local calendar* — a daily rollup, a partition boundary, a cache key — still moves with the reader's zone regardless of how the timestamp is written. Two related hazards: reading the local zone consults `TZ`, so any runtime `set_var("TZ", …)` races every thread reading local time (UNSAFE-8 — `set_var` is `unsafe` in the 2024 edition); and `chrono` versions before 0.4.20 called `localtime_r` unsoundly (RUSTSEC-2020-0159), so treat a pinned older `chrono` in `Cargo.lock` as a finding
- **TIME-3.** Distinguish *elapsed-time* arithmetic from *calendar* arithmetic. `TimeDelta::days(7)` (the type `chrono::Duration` was renamed to in 0.4.35 — the old alias is still exported and collides with `std::time::Duration` when both are in scope) is exactly 604 800 seconds; `Days::new(7)` is "the same wall-clock time, seven calendar days later". They differ by an hour across a DST transition and they differ again for `Months::new(1)`, which has no fixed length at all. Rule of thumb: timeouts, TTLs, and rate windows are `TimeDelta`; billing periods, schedules, reminders, and retention windows a human described in days or months are `Days`/`Months` via `checked_add_days` / `checked_add_months`. The panic risk splits across two stages, and conflating them hides one of them. **Construction**: `TimeDelta::days(i64)` panics when the value exceeds `TimeDelta`'s range — `try_days` returns `Option` instead — whereas `Days::new(u64)` and `Months::new(u32)` are infallible `const fn`s that only wrap a count and cannot fail. **Application**: `+` *and* `-` panic on overflow for all three, and the checked forms return `Option` — `checked_add_signed` / `checked_sub_signed` for a `TimeDelta`, `checked_add_days` / `checked_sub_days` / `checked_add_months` / `checked_sub_months` for the calendar types. Subtraction is the half that gets forgotten: `expiry - TimeDelta::days(n)` and `now - Days::new(n)` panic on underflow exactly as their `+` counterparts do on overflow. So `now + TimeDelta::days(untrusted)` has two panic sites and `now + Days::new(untrusted)` has one; both are remote panics on untrusted input (SEC-33), and the fix in either case is the checked form. Adding a `Months` value that overflows the target month saturates to the last valid day (Jan 31 + 1 month = Feb 28/29), which is usually what is wanted but must be stated in tests
- **TIME-4.** Measure elapsed time with a monotonic clock — `std::time::Instant` (or `tokio::time::Instant` in async) — never by subtracting two `Utc::now()`/`SystemTime` readings. The wall clock is adjusted by NTP, leap-second smearing, and the operator, so it can jump backwards; a wall-clock delta can come out negative, absurdly large, or silently wrong, which turns a latency metric into noise and a hand-rolled timeout into a hang. Conversely, `Instant` is meaningless across processes and cannot be serialized or persisted — a value that must outlive the process (an expiry stored in a database, a token `exp`, a scheduled run time) is a `DateTime<Utc>`. Flag `let start = Utc::now(); … (Utc::now() - start)` and the `SystemTime::now()` / `duration_since(start)` form of the same mistake around any timed operation; use `Instant::elapsed()`
- **TIME-5.** Keep timestamps unambiguous at every boundary. `NaiveDateTime` carries no offset — a naive value that is *meant to be an instant*, parsed from input or serialized out, silently means "whatever zone the reader assumes", so keep it confined to the parse step and attach a zone (`and_utc()`, `from_local_datetime`, which returns a `LocalResult` because DST makes some local times ambiguous or nonexistent — do not `.unwrap()` it) before the value escapes the function. This applies to instants only: `NaiveDate` is the *correct* type for a value that is genuinely a calendar date and not a point in time — a birth date, an invoice or billing date, a holiday, a contract term — and forcing a zone onto one is the opposite bug, because converting it through midnight shifts the date itself. The review question is which of the two the value is, not whether the type carries a zone. For interchange, emit RFC 3339 explicitly with `to_rfc3339()` / `to_rfc3339_opts()` and parse with `DateTime::parse_from_rfc3339`: the `Display` impl is a *different*, space-separated format and is not a wire format. Integer timestamps must state their epoch and unit in the type or the field name (`expires_at_unix_ms`, `chrono::serde::ts_seconds` / `ts_milliseconds`) — a bare `i64` field is the seconds-vs-milliseconds bug waiting to happen. Reject a `%Y-%m-%d %H:%M:%S` string stored or transmitted with neither an offset nor a named zone beside it *when the value is an instant*. Local wall-clock time plus an IANA zone name in a separate field is the **correct** encoding for a future scheduled event — "09:00 in Europe/Lisbon on 2027-03-30" must re-resolve against the tzdb at firing time, and freezing it to an instant or an offset today is the bug, because the offset for that date can still change
- **TIME-6.** Do not read the clock in the middle of business logic — `Utc::now()`, `SystemTime::now()`, `Local::now()`, `Zoned::now()`, `Instant::now()` for a decision rather than a measurement (TIME-4), any of them. A function that reads the clock internally cannot be tested at a boundary (month rollover, expiry ±1s, a leap day, a DST transition) without sleeping or mutating the machine's clock, and its tests go flaky the moment CI runs them at midnight (TEST-16, TEST-18). Take the instant as a parameter (`fn is_expired(&self, now: DateTime<Utc>) -> bool`) or inject a clock trait — `trait Clock { fn now(&self) -> DateTime<Utc>; }`, or whatever instant type the code already uses (`SystemTime`, `Zoned`) — with a fixed-time test impl; call the real clock once, at the edge, and thread the value down. In async code, `tokio::time::pause()` covers timer-driven waits (TEST-13) but does *not* affect `Utc::now()` — only an injected clock does

## Rust 2024 Edition Reference

> These are **not finding-generating rules** — they document edition behavior changes for context. The compiler and `cargo fix --edition` enforce edition migration. Reviewers should understand these changes but should not flag them as findings.

- **EDITION-1.** Reserved keyword: `gen` (for future generators); use raw identifier `r#gen` if needed
- **EDITION-2.** `impl Trait` captures all lifetimes by default; use `+ use<'a, T>` syntax to explicitly specify captures
- **EDITION-3.** Match ergonomics restrictions: in Rust 2024, you cannot mix implicit match ergonomics (compiler-inserted `ref`/`ref mut`) with explicit `mut` or `ref` on the same binding — it's a hard error. Fix: either let the compiler handle binding modes entirely, or write fully explicit patterns. Patterns that already specify all binding modes are unaffected
- **EDITION-4.** Shortened temporary lifetimes: `if let` temporaries drop at branch end, not statement end
- **EDITION-5.** Apply edition migration fixes before updating `edition = "2024"` in Cargo.toml
