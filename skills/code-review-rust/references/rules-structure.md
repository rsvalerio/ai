# Structure and Readability Rules

## Functions & Structure (typical severity: Medium--High)

> Thresholds below are industry-common defaults (Clean Code, cognitive complexity research). Adjust per project — the goal is flagging outliers for review, not rigid enforcement.

- **FN-1.** Functions ≤50 lines. Each function should operate at a single abstraction level — extract low-level details into named helpers rather than mixing orchestration with bit manipulation or I/O. Context may justify exceptions (state machines, exhaustive match arms, DSL builders)
- **FN-2.** Nesting ≤4 levels; use early returns/guards. Transform nested conditionals: `let Some(x) = input else { return Err(...) };` (let-else, stable since 1.65), `if !precondition { return early; }` (guard clause), or let-chains (`if let Some(x) = opt && x.is_valid() { ... }`, stable in Rust 2024) instead of nested `if let` pyramids
- **FN-3.** Parameters ≤5; group into config structs. Beyond ~4 parameters the failure mode is not length but **mix-ups** — `new(bank: &str, customer: &str, currency: &str, amount: u64)` accepts any permutation of the three `&str`s and compiles. Two fixes compose: newtype the primitives so the compiler rejects the swap (API-2), and *cascade* the construction, grouping parameters into the intermediate types the domain already has (`Deposit::new(account: Account, amount: Currency)`, with `Account::new(bank, customer)` one level down). Beyond 4 optional parameters, a builder is the answer instead (API-4).
  **Ordering is part of the signature.** When the same conceptual parameters recur across functions — in a crate or across a family of crates — they must appear in the same order every time: call-specific parameters first, ubiquitous ones (`&logger`, `&ctx`) last, closures always last, and no more than one closure. A `tenant_id, user_id` here and `user_id, tenant_id` there is a bug waiting for two same-typed arguments to meet
- **FN-4.** Return structs, not long tuples
- **FN-5.** Extract complex booleans (>3 conditions) to named predicates: `is_<state>` for state checks (`is_ready`, `is_valid`), `has_<possession>` for ownership/presence (`has_data`, `has_permission`), `should_<action>` for conditional actions (`should_retry`, `should_log`), `can_<capability>` for ability checks (`can_read`, `can_connect`)
- **FN-6.** Cyclomatic complexity ≤10 (McCabe's threshold, widely adopted); `clippy::cognitive_complexity` catches the mechanical threshold — this rule's unique value is the Rust-specific nuance: exhaustive pattern matching naturally inflates cyclomatic complexity, so parsers, state machines, and exhaustive matches may exceed this; evaluate cognitive load (READ-1) rather than forcing extraction
- **FN-7.** *Retired* — folded into **READ-1** and **READ-3**. Iterator-chain length is a readability concern, not a structural one; Clippy handles the mechanical cases (`manual_map`, `manual_flatten`, `manual_filter_map`).
- **FN-8.** DRY: see DUP-1--10 for thresholds and refactoring guidance. Clone abuse: see OWN-8 and PERF-3
- **FN-9.** Explicit dependencies; no implicit state

## Readability

- **READ-1.** Prefer clarity over cleverness: explicit > implicit, familiar patterns > obscure features, readability > brevity
- **READ-2.** Break dense expressions into named intermediate variables
- **READ-3.** Name steps in long iterator chains. When a chain exceeds ~3--4 combinators or mixes control flow with data transformation, either break it into named intermediates (`let parsed = items.iter().map(...).collect::<Result<Vec<_>, _>>()?;`) or switch to an explicit `for` loop. Clippy handles the mechanical cases (`manual_map`, `manual_flatten`, `manual_filter_map`); this rule covers the structural upper bound
- **READ-4.** Document "why", not "what"
- **READ-5.** Make invariants explicit (types, asserts, docs)
- **READ-6.** Consistent patterns for similar problems
- **READ-7.** Prefer pattern matching over nested if/else; compiler enforces exhaustiveness. Note: clippy catches narrow cases (`match_like_matches_macro`); this rule covers the broader stylistic preference
- **READ-8.** For new service/application code, prefer the `tracing` crate over `log` — structured fields, spans, and per-async-task context are first-class, and most modern observability exporters (OpenTelemetry, Honeycomb, Datadog) target `tracing::Subscriber`. The `log` crate is still appropriate for libraries that want a minimal dependency footprint; bridge library logs into `tracing` with `tracing-log`. Flag `println!`/`eprintln!` in non-binary, non-test code as a finding. **In CLI binaries**, where direct printing is correct, honour the stream contract: `stdout` carries the program's *result* (the part a caller may pipe or parse), `stderr` carries diagnostics, progress, warnings, and errors. Any `println!` used for a diagnostic breaks downstream pipelines and must be `eprintln!`
- **READ-9.** `dbg!` must not survive into committed code. It writes the expression source and value to stderr *unconditionally* — it is not stripped in release builds, unlike `debug_assert!` — so a leftover call becomes permanent noise on the diagnostic stream and can leak internal state (SEC-21). It also takes ownership of its argument, so inserting or removing it can change move semantics. Enable `clippy::dbg_macro` (restriction lint) at deny level in CI to catch it mechanically; use `tracing::debug!` for logging that is meant to stay
- **READ-10.** Prefer `#[expect(lint, reason = "…")]` over `#[allow(lint)]` for suppressions that are meant to be temporary or that document a specific known violation (both `expect` and the `reason` field are stable since Rust 1.81). `#[expect]` suppresses the lint exactly like `#[allow]`, but additionally warns (`unfulfilled_lint_expectations`) once the lint stops firing — so the suppression deletes itself from the codebase instead of outliving the problem it was hiding. `#[allow]` remains correct for permanent, intentional policy exceptions. **Footgun:** an `#[expect]` on a lint that fires only under some cfg/feature combinations produces `unfulfilled` warnings in every other configuration, so use `#[allow]` for cfg-dependent suppressions or scope the expectation to the same `#[cfg]`. Per rules-classification, a suppression carrying a specific, accurate `reason` earns the one-level severity reduction; a bare `#[allow]` with no rationale does not
- **READ-11.** A hardcoded value in production code needs a comment saying *why that value*, what breaks if it changes, and which external system it is pinned to — and it should be a named `const` rather than an inline literal. `wait_timeout(60 * 60 * 24)` is transparently a day and opaque as to why a day; a `const UPSTREAM_SERVER_TIMEOUT: Duration` whose doc comment says "based on `api.foo.com`'s own timeout policy; lower values abort valid requests" is a value the next person can safely change. This is READ-4 applied to constants, and it is what makes a magic number auditable rather than load-bearing folklore. Highest value on timeouts, retry counts, buffer and batch sizes, capacity thresholds, protocol version numbers, and wire-format offsets. Ordinary literals with local, obvious meaning (`0`, `1`, `2` as an index or step) are not the target
- **READ-12.** Log structured events with named fields and a message *template*, not a preformatted string. `tracing::info!("file opened: {}", path)` bakes the value into the message text, so nothing downstream can filter, group, or aggregate on the path; `info!(file.path = %path.display(), "file opened")` records it as a typed field that the subscriber and the collector can both address. Be accurate about the cost, because the usual form of this argument is wrong: `tracing`'s macros test whether the event is enabled before evaluating their arguments, and carry the message as `fmt::Arguments` for the subscriber to render, so the positional form is not itself an eager allocation. The eager cost belongs to an explicit `format!()` built and passed *into* the call, which allocates whether or not anyone is listening (PERF-19). Queryability, not allocation, is the reason to prefer named fields. Three conventions worth holding to: (1) **name the event** — a stable hierarchical identifier (`<component>.<operation>.<state>`, e.g. `file.processing.success`) lets a query group occurrences across every field permutation, where a message string cannot; `tracing`'s `event!` accepts `name:` for this. (2) **Use OpenTelemetry semantic conventions** for field names that have them — `http.request.method`, `http.response.status_code`, `url.path`, `server.address`, `db.system.name`, `db.operation.name`, `file.path`, `error.type` — so the event is legible to the collector without per-service mapping rules. (3) **Redact at the emission site**, not in the pipeline: emails, user-identifying paths, tokens embedded in filenames, and PII in payloads must not reach the field in the first place (SEC-21). Note that message templates carrying literal `{{field}}` placeholders will trip `clippy::literal_string_with_formatting_args`; allow that lint deliberately if you adopt the convention (READ-10)
- **READ-13.** Documentation describes the end state, not the journey that produced it. Crate, module, and item docs that narrate *how a change was designed* — "why we picked X over Y" essays, migration notes, design journals, and self-report tables of which guidelines a change followed — are process artifacts: they are meaningless to a reader using the API, and they go stale on the next change while looking authoritative. This is a common shape in agent-authored diffs; flag it in `//!` and `///` blocks and in the public README. What *is* legitimate is a "Design principles" section describing enduring, user-relevant properties — the crate is allocation-free, `#[no_std]`-compatible, single-threaded by design. The rule of thumb: if the text would be deleted verbatim by someone who joined after the decision, it belongs in the PR description or an ADR, not in the docs

## Architecture & Modules

- **ARCH-1.** No god objects or god modules; split by responsibility. Module-level red flags: >500 lines, mixed unrelated concerns (e.g., parsing + networking + serialization in one file), >10 public items with no cohesive theme
- **ARCH-2.** At module boundaries, depend on traits for decoupling and testability; within a module, start concrete until abstraction is justified (see TRAIT-9 for when to extract traits)
- **ARCH-3.** Modules by concern (`auth`, `db`, `error`), not layer — anti-pattern: `models/`, `controllers/`, `services/` directories that scatter a single feature across many folders; instead, group by domain so related types, logic, and tests live together. Module *layout* follows the same logic as menu design: the handful of items a user must find to use the crate at all belong in the **root** (a `foo_client` crate's `Client`), and everything else groups into submodules named for the use case — `account`, `network`, `status`, never `traits`, `errors`, or `types`, which sort items by what they are rather than what they are for. Both extremes are findings: a flat root of dozens of unordered public items, and a root with nothing in it behind a wall of submodules. (Generated `-sys` crates and genuine umbrella crates are the exceptions.) Submodules are also where subsystem-level documentation belongs (API-14)
- **ARCH-4.** Shared code used by multiple concerns should be organized as its own concern-named module (e.g., `crypto`, `field_path`, `json_fields`) rather than generic buckets like `helpers`/`utils`. Cross-module dependencies are normal; keep them explicit, one-directional, and keep public API re-exports curated in `lib.rs`. If the code is purely implementation detail, prefer an `internal` module with descriptive submodules over a grab-bag utility module.
- **ARCH-5.** High cohesion within modules; no circular dependencies
- **ARCH-6.** Match abstraction to problem complexity; YAGNI
- **ARCH-7.** Prefer flat file layout (e.g., `foo.rs` + `foo/bar.rs`) over `mod.rs` for new code; both are idiomatic — follow project convention when one exists
- **ARCH-8.** `lib.rs` = thin entry point: module declarations, re-exports, crate-level docs, and small central types only. Move out: error types (→ `error.rs` when >50 lines or shared across modules), implementation logic, private helpers, domain logic. Organization heuristic: inline error types for ≤2 types in ≤50 lines; when types exceed ~50 lines or you have 3+ helper functions, extract to a dedicated module
- **ARCH-9.** Minimal public surface; hide internals behind modules
- **ARCH-10.** Snake_case files; singular names (`config.rs` not `configs.rs`)
- **ARCH-11.** In Cargo workspaces, centralize shared dependency versions and lints in `[workspace.dependencies]` and `[workspace.lints]`, then inherit with `dep = { workspace = true }` and `[lints] workspace = true`. Prevents version drift across member crates and makes CVE upgrades a single-point change. Flag workspaces where sibling crates pin different versions of the same transitive dep or duplicate lint configuration. Three details that make this actually hold: (1) declare **every** dependency in `[workspace.dependencies]`, including ones only a single crate uses, so there is one place to audit; (2) declare them with `default-features = false` and let members opt into the features they need, since a workspace-level feature is silently unified into every member (ARCH-12); (3) **workspace members are dependencies too** — `sibling = { path = "crates/sibling", version = "0.5.2" }` in `[workspace.dependencies]` with `sibling.workspace = true` in the member, not a bare `sibling.path = "../sibling"` in each crate, which publishes unversioned and resolves inconsistently.
  `[workspace.lints]` is also where the project's static-verification policy lives, and an empty one is a finding on its own. A reasonable baseline turns on the compiler lints that are off by default (`missing_debug_implementations`, `unsafe_op_in_unsafe_fn`, `unused_lifetimes`, `redundant_lifetimes`, `redundant_imports`, `trivial_numeric_casts`, `ambiguous_negative_literals`) and the major clippy groups (`correctness`, `suspicious`, `complexity`, `perf`, `style`, `pedantic`, `cargo`) at `warn` with `priority = -1`, plus a few `restriction` lints that pay for themselves — `undocumented_unsafe_blocks` (UNSAFE-1), `allow_attributes_without_reason` (READ-10), `unused_result_ok`, `map_err_ignore`, `clone_on_ref_ptr`, `dbg_macro` (READ-9). Opt back out case by case rather than not enabling them. Beyond lints, CI should carry `cargo audit` (SEC-27), `cargo-udeps` for dependencies nothing imports, `cargo-hack` to prove the feature combinations actually build (ARCH-12), and `cargo miri test` where the crate has `unsafe` (UNSAFE-10)
- **ARCH-12.** Enforce feature-flag invariants with `compile_error!` rather than a runtime check or a silent fallback. Cargo features are *additive* — any consumer in the dependency graph can turn one on, and `--all-features` turns on every one — so a crate whose backends are mutually exclusive, or that requires at least one of a set, must say so at compile time:

  ```rust
  #[cfg(not(any(feature = "sqlite", feature = "postgres")))]
  compile_error!("enable exactly one backend: `sqlite` or `postgres`");
  #[cfg(all(feature = "sqlite", feature = "postgres"))]
  compile_error!("`sqlite` and `postgres` are mutually exclusive");
  ```

  Cover both directions (none-selected *and* over-selected); a single `not(any(...))` guard still lets `--all-features` produce a nonsense build. Prefer restructuring so features are genuinely additive (e.g. select the backend at runtime from a trait object) — mutually exclusive features are a design smell that breaks feature unification for downstream crates. Additive means, concretely: enabling a feature may add public items but must never **remove or change** one (adding enum variants is fine only behind `#[non_exhaustive]`, API-9); a feature must not require the user to also enable another one by hand; a feature must not depend on its parent *not* enabling something in a child; and there is no such thing as a `no-std` feature — invert it into a `std` feature, because `--all-features` and feature unification will otherwise turn `no_std` on for someone who wanted the opposite. `cargo hack --feature-powerset check` is how you find out whether any of this is true. `compile_error!` is the right tool where that restructuring is not possible, and inside declarative/procedural macros to reject invalid invocations with a readable message
- **ARCH-13.** Code ported from C#, Java, C++, or Python must be reshaped, not transliterated. Separate the two halves of a port: the *domain* logic — a pricing rule, a parser, a state machine — should come across nearly unchanged, while the *language* scaffolding around it should not survive at all, because it exists to solve problems the source language has and Rust does not. Scan signals, each of which usually indicates a mechanical translation: a `throw_if_null` / `check_not_null` helper (Rust has `Option`); an interface-per-service trait implemented exactly once and passed as `dyn` (API-18); `Arc` at every field because the source language boxed everything (PERF-17); a `Manager`/`Service`/`Factory` type (API-1); inheritance simulated through `Deref` (OWN-12); a global registry or singleton static (CONC-10); exceptions modelled as panics (ERR-11); manual `Dispose`-style teardown methods where `Drop` belongs. The most deceptive cases are the constructs that *do* translate superficially and diverge later — statics, reflection substitutes, lifetime-free object graphs. A striking structural resemblance between the Rust and the original is the finding, not the achievement
- **ARCH-14.** In an FFI project, business logic lives in the core crate and the FFI crate only translates. `foo` should be ordinary, safe, testable Rust that knows nothing about C; `foo-ffi` owns the `extern "C"` entry points, the raw pointers, the ownership handoffs, and the error-code mapping (SEC-34--36, SEC-39). The failure mode is letting interop requirements leak inward — `#[repr(C)]` on a domain type, a struct flattened into `(ptr, len, capacity)` fields, an owned `Vec` replaced by a raw pointer — which makes the core crate untestable in Rust terms and pins its data model to a foreign ABI forever. Accept the duplication: an FFI entry point that collapses several core calls into one C-shaped function is the correct shape, not a smell. Two conventions ride along: name crates by direction (`-sys` for bindings *into* an existing C library, `-ffi` for a Rust library exported *to* C), and where a type wraps a native handle, provide `unsafe fn from_native(h) -> Self` plus `to_native`/`into_native` escape hatches with their contracts documented, so a caller holding a handle from elsewhere is not forced to fork the crate
- **ARCH-15.** Workspace layout: one `Cargo.toml` at the root, all crates as siblings in a single directory (`crates/`), and a shallow grouping (`common/`, `server/`, `client/`) only past a dozen or two. A crate nested inside another crate's directory — worst of all inside its `src/` — is never right; express the relationship with a name prefix instead (`foo`, `foo_core`, `foo_proc`). **When in doubt, split.** Rust compiles a crate as a unit, so a large crate serializes work that separate crates parallelize and recompile independently; if a submodule could stand on its own, it should be its own crate. The split also breaks `pub(crate)` shortcuts, which is usually the design feedback you wanted. Re-join for the user with an umbrella crate where the split was purely technical (a `foo_proc` proc-macro crate must be re-exported from `foo`, MACRO-3). Rule of thumb for the crate-versus-feature choice: a **crate** is for functionality that can be used on its own; a **feature** unlocks functionality that cannot
- **ARCH-16.** A published library must build with nothing but `cargo` and `rustc`. Users install crates whose dependency trees run into the hundreds and expect `cargo build` to just work — so a crate that needs `perl`, `cmake`, cross-compilers, a `protoc` binary, or an environment variable to compile imposes that on every transitive consumer, most of whom have never heard of it. Run code generation (protobuf, bindgen, parser generators) at *publish* time and ship the generated `.rs` files in the crate. Unless the crate is obviously platform-specific, it must build on all Tier 1 targets — introduce an internal HAL module with a `dummy` fallback rather than `#[cfg]`-ing a hole into the build. For a `-sys` crate wrapping a native library: drive the build from `build.rs` via the `cc` crate rather than invoking Makefiles or shell scripts, vendor the upstream sources into the crate (recording the git URL and hash so they are verifiable), make optional tools like `nasm` genuinely optional, pre-generate the `bindgen` glue, and support dynamic loading (`libloading`) alongside static linking. Where sources are too large for crates.io and must be downloaded, pin their hashes and allow an env-var override of the source root so hermetic builds are still possible
- **ARCH-17.** A **new** crate or workspace should be created on the latest stable edition (2024 at the time of writing); the `resolver` key is implied by the edition and not needed. Unlike an MSRV bump (API-15) this costs nothing in compatibility — editions are per-crate, and a 2015-edition binary links 2024-edition libraries without issue — so an old edition on new code buys nothing and locks the crate out of let-chains (FN-2), `gen`, the `unsafe_op_in_unsafe_fn` default, and the 2024 match-ergonomics rules. Scope: this is about the edition a crate is *created* on. Migrating an existing crate is the compiler's and `cargo fix --edition`'s job and is not a finding — see the `EDITION-*` reference notes in rules-core.md

## API Design (typical severity: Medium)

- **API-1.** Expressive type names (`TemperatureCelsius`, not `f64`) — expressive, but **short**: Rust convention is that identifiers compound at most two short words (`AppConfig`, not `GlobalApplicationConfig`), that module and crate names are not repeated in item names (`foo::Id`, not `foo::FooId` — callers disambiguate locally with `foo::Id` vs `bar::Id`), and that established abbreviations are preferred (`CallbackFn` over `CallbackFunction`). Exceptions are fine where they earn it, but should be exceptional per crate.
  **Names must also be free of weasel words** — `Service`, `Manager`, `Factory`, `Helper`, `Handler`, `Info`, `Data` — which name a role every type already has and so carry no information. A type holding bookings is `Bookings`; if it does something more specific, say that (`BookingDispatcher`). "Manager" is almost always either a collection or a lifecycle concern, and lifecycle in Rust belongs to `Drop`, not to a manager. "Factory" has a canonical Rust spelling, `Builder` (API-4) — and note that a function needing repeatable construction should take an `impl Fn() -> Foo`, not a `FooBuilder` parameter, which is an OO import
- **API-2.** Newtype pattern: wrap primitives for type safety (`UserId(u32)`, `Email(String)`) to prevent argument order mistakes; zero-cost abstraction. "Zero-cost" is a statement about performance, not about layout: a plain `struct UserId(u32)` has *no guaranteed* ABI or memory layout, so passing it across FFI, `transmute`-ing it, or casting `&[UserId]` to `&[u32]` is unsound. Add `#[repr(transparent)]` when any of those matter — it guarantees the type has exactly the layout and ABI of its single non-zero-sized field (other fields must be zero-sized, e.g. `PhantomData`). Required on newtypes crossing an FFI boundary (SEC-36) and on wrappers the caller may reinterpret; unnecessary noise on ordinary domain newtypes that never leave Rust.
  **A newtype that encodes an invariant must enforce it**, or it is a rename with extra steps: `pub struct Month(pub u8)` with a `Month::new(u8) -> Self` leaves every caller re-checking `1..=12`, which is the exact duplication the type existed to remove — and the public field lets anyone bypass the check anyway. For any newtype whose domain is narrower than its representation (non-empty string, percentage, port, sanitized path, validated identifier): keep the field private; provide at least one **fallible** constructor (`fn from_u8(v: u8) -> Result<Self, _>`, or `TryFrom`/`FromStr`); make conversions from the weaker type fallible, which means **no infallible `From<u8>`**; and where a panicking constructor is also offered for literals, make it `const fn` so `const { Month::new(14) }` fails at compile time instead of in production (PATTERN-2, CL-3)
- **API-3.** Prefer returning `impl Iterator` over collected `Vec` when the caller only needs iteration; return `Vec` when indexing, length, or owned storage is required
- **API-4.** Builder pattern for complex construction; initialize all fields. A builder is an API decision, not decoration — justified when the type has many optional fields, when construction validates or carries ordering semantics, or when positional arguments would be ambiguous (FN-3); for inert data, a public struct with `..Default::default()` is simpler and better (DUP-7). Where one *is* warranted, generate it (`bon`'s `#[builder]`, applicable to structs, functions, and methods; alternatives `typed-builder`, `derive_builder`) rather than hand-writing it: handwritten builders are pure boilerplate (DUP-3) and drift from the type they construct, so a newly added field silently has no setter and callers cannot set it. `bon` additionally enforces required fields at compile time through typestate, which removes the runtime "field not set" error arm that hand-rolled builders otherwise carry — and preserves the point of a builder over a public struct: the API can gain fields without forcing every callsite into a giant struct literal.
  **Shape conventions**, whether generated or hand-written: the builder for `Foo` is `FooBuilder`, reached through `Foo::builder()` and not through a public `FooBuilder::new()`; setters are chainable and named for the value (`.name(x)`, never `.set_name(x)`); the terminal method is `.build()`. **Validation belongs in `.build()`, not in the setters** — a fallible setter (`.name("x")?.distance(42)?`) forces an error check at every step, still cannot express constraints *between* fields, and clutters the happy path, so accept values freely and return `Result` from `build()` once. Better still, let the field types validate themselves (API-2) so `build()` only checks the cross-field rules. **Required** parameters are not setters at all: pass them when creating the builder, `Foo::builder(deps)`, and where there are several, group them into a `FooDeps` struct taken as `impl Into<FooDeps>` so `Foo::builder(logger)`, `Foo::builder((logger, config))`, and the explicit struct all work — which also lets a new required parameter be added without breaking callers
- **API-5.** `#[must_use]` on Results, Futures, builders. Note that `Result`, `Option`, and futures are *already* `#[must_use]` in std, so annotating a function returning one adds nothing — the value is in annotating (a) **your own types** whose construction is pointless if discarded (`#[must_use = "remember to execute the query"] struct Query(…)`, guards, builders mid-chain), and (b) functions returning a plain type where discarding signals a bug (`Vec::is_empty`, a pure transform mistaken for an in-place mutation). Always use the message form `#[must_use = "…"]`: the bare attribute produces "unused return value that must be used", which tells the reader nothing they could not see. Write the message as the action the caller forgot, not as a restatement of the warning
- **API-6.** Doc tests with `///`
- **API-7.** Prefer returning values over out params (`&mut T`); out params are acceptable for buffer reuse (`Read::read`, `Write::write`) and allocation-sensitive hot paths
- **API-8.** Sealed trait pattern: prevent external implementations to reserve right to add methods without breaking changes; use private `Sealed` supertrait
- **API-9.** Prevent external construction/exhaustive-match when reserving the right to add fields or variants: use `#[non_exhaustive]` on public structs and enums (stable since Rust 1.40) — it is the idiomatic and tool-aware mechanism (`cargo semver-checks` understands it). Reach for the `_private: ()` field pattern only when you need to forbid construction *and* still allow pattern matching on all other public fields, which `#[non_exhaustive]` cannot express on its own
- **API-10.** For published libraries, run `cargo semver-checks` in CI on every release: it detects accidental breaking changes (removed items, changed signatures, added required trait bounds, changed MSRV) that pure version bumps won't catch. Pair with `cargo public-api --diff-git-checkouts` for a human-readable diff of the public surface
- **API-11.** Retire public API through `#[deprecated(since = "…", note = "use `X` instead")]` rather than deleting it. Deprecating is a non-breaking, minor-version change; removal is a major-version break, so the attribute buys a migration window in which callers get a compiler warning naming the replacement. Applies to functions, types, traits, modules, constants, and type aliases — but **not** trait impls, where it is silently useless (`useless_deprecated` lint). Two review checks: (1) `since` must be the version the deprecation *ships in*, not the version it will be removed in — a wrong `since` breaks `#[deprecated]`'s interaction with `cargo semver-checks` (API-10) and misleads readers; (2) `note` must name the concrete replacement, since a note saying only "deprecated" leaves the caller no path forward. Deprecated items still warn at internal call sites — migrate those in the same change rather than papering over them with `#[allow(deprecated)]`, and when a genuine internal use must remain (e.g. implementing the deprecated item in terms of the new one), scope the allow to that item with a reason (READ-10)
- **API-12.** When UTF-8 paths are already part of the product contract — paths serialized into JSON, compared in config files, stored in a database, printed in diagnostics, or returned through an API — encode that in the type with `camino`'s `Utf8Path`/`Utf8PathBuf` instead of converting at every boundary. `Path`/`PathBuf` are correct precisely because OS paths are *not* guaranteed UTF-8, but in code that assumes UTF-8 anyway they push the assumption down into every callsite in one of three bad forms: `.to_str().unwrap()` (a panic on input the code claims to support), `.to_string_lossy()` (silent replacement-character corruption of a real filename), or an `.ok_or(…)` arm producing an error no caller can act on. `Utf8PathBuf` keeps the full path API, states the invariant once, and yields `Display`, `&str`, and serde support for free — API-2's newtype argument applied to a std type. Highest value in CLIs, build tools, config-heavy applications, developer tooling, and test infrastructure. **Do not adopt it** in tools that must faithfully round-trip arbitrary platform paths (backup, archiving, filesystem utilities, package managers) — there the lossiness is the bug. Scan signal: repeated `to_str().unwrap()` / `to_string_lossy()` on the same path values across a module
- **API-13.** A public item should be reachable by exactly **one** path. `crate::db::Connection` that is also `crate::Connection` doubles every mention of the type in docs, search results, and error messages, and leaves readers unsure whether the two are the same type. This is a characteristic artifact of iterative refactoring — the old path is re-exported "for compatibility" and never removed — so treat a `pub use` that merely duplicates a still-public path as the finding. Re-exporting from a `pub(crate)` module to lift an item into the root is the *correct* use of `pub use`; the item then has one public path. Related surface-hygiene rules, all with the same motive: **no glob re-exports** (`pub use foo::*` exports whatever is added later and is unreviewable in a diff — enumerate them, `pub use foo::{A, B, C}`; the accepted exception is `#[cfg]`-gated platform HAL modules where exactly one glob is live per target); **no `prelude` module** — preludes exist in `std` to carry edition items, and in a crate they only collide (`use foo::prelude::*; use bar::prelude::*;` → `error[E0659]: Client is ambiguous`), and a crate that "needs" one is telling you its module layout is wrong (ARCH-3); **foreign types come from their own crate** — if you accept `bar::Url`, let users depend on `bar`, rather than `pub use bar::Url` creating a second alias for a type that already has a name (umbrella crates and technical splits excepted); and mark genuine `pub use` re-exports `#[doc(inline)]` so they render with their siblings instead of as an opaque re-export block — except for `std` and third-party types, which should stay un-inlined precisely so readers can see they are foreign.
  The same reasoning limits *which* types the surface commits to: **every type in a public signature becomes part of your contract**, and only `std` types carry a permanent stability guarantee. Prefer them; leak a third-party type only behind a feature flag (`serde`), from a sibling of the same umbrella crate, or where the interoperability gain is substantial and deliberate. Every other leak pins your major version to someone else's
- **API-14.** Public items carry the canonical doc sections, and a module has module docs. The summary sentence is mandatory; `# Examples` is strongly encouraged; `# Errors` (when returning `Result`), `# Panics` (when it can panic), `# Safety` (on any `unsafe fn`, listing what the caller must uphold), and `# Abort` (when the process can die, e.g. an FFI unwind, SEC-39) are mandatory **when applicable** — `clippy::missing_errors_doc` / `missing_panics_doc` / `missing_safety_doc` cover part of this mechanically. Do not write a `# Parameters` table: parameter behaviour goes in prose that names the arguments — "Copies a file from `src` to `dst`." The **first paragraph**, meaning everything up to the first blank line, is what rustdoc lifts into the module index — not the first sentence, and not the first source line. So the summary must be followed by a blank line, and wrapping it across source lines changes nothing. Length is what matters: keep it to roughly **15 words** and let the body carry the rest (`clippy::too_long_first_doc_paragraph` measures the paragraph, and is the mechanical check). Every public module needs a `//!` block, and it is the right place for what individual item docs cannot say: what the module contains, when *not* to use it, worked examples, subsystem-level specifications (the way `std::fmt` documents its format language), observable side effects and what is guaranteed about them, and which system APIs are used underneath
- **API-15.** A library sets an MSRV (`rust-version` in `Cargo.toml`) when it is created, keeps it a few releases behind current stable, and raises it in a **minor** version. Both halves are findings: a library with no declared MSRV has an accidental one that changes with whatever the maintainer happened to compile with, and a library pinned to a years-old compiler forces its own code away from stabilized idioms for users who almost certainly are not on that compiler. Bumping is not a breaking change by ecosystem convention — every crate with dependencies is already bound to that convention — and treating it as major-worthy fragments downstream trees for no benefit. The practical consequence for review: rules here that name a stabilization version (ASYNC-11, TRAIT-10, CONC-10, VER-*) are gated on the project's declared MSRV, not on current stable
- **API-16.** These rules complement the upstream [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/checklist.html), the [Rust Style Guide](https://doc.rust-lang.org/nightly/style-guide/), and the [Rust Design Patterns](https://rust-unofficial.github.io/patterns/) book rather than replacing them. Four upstream items are forgotten often enough to name here: **C-CONV** — ad-hoc conversions follow the `as_` (borrowed→borrowed, cheap) / `to_` (expensive or owned) / `into_` (consuming) prefixes, and getting them wrong misleads about cost; **C-GETTER** — a getter is `fn name(&self)`, not `fn get_name(&self)`; **C-CTOR** — constructors are inherent associated functions, and a type with `Default` should still have `Foo::new()`; **C-COMMON-TRAITS** — implement `Copy`, `Clone`, `Eq`, `PartialEq`, `Ord`, `PartialOrd`, `Hash`, `Default`, `Debug` eagerly where the semantics hold, because adding them later is a chore for users and cannot be done by them (subject to TRAIT-4's "derive with intent" and SEC-5 for secret-bearing types). Add `Display` for any type a human is meant to read — error types (required by `std::error::Error`), identifiers, and string-like wrappers — rendering it the way Rust customarily does, and never including data that must not be logged (SEC-21)
- **API-17.** Associated functions are for constructing the type, not for hosting general computation. Rust has free functions as first-class citizens, so a helper that does not act on a receiver does not need an `impl` block to live in — `Database::check_parameters(p)` should be `fn check_parameters(p: &str)` in the module. This is one of the most reliable tells of code ported from a language where every function must belong to a class (ARCH-13), and it costs callers a qualifier on every use for no gain. `Foo::new`/`Foo::with_*` (construction, C-CTOR) and trait associated functions (`Default::default`, `FromStr::from_str`) are of course idiomatic
- **API-18.** Prefer **concrete types over generics, and generics over `dyn Trait`**, and do not let any of them show through the public surface as nesting. Reach down the ladder only when the rung above stops working: start with a concrete type; where a second implementation exists purely for testing, use a private enum core with a feature-gated mock arm rather than a trait (TEST-33); where *users* need to supply implementations, introduce narrow traits (`StoreObject`, `LoadObject`, not one `Database` interface — ISP, TRAIT-6) and accept them as `impl Trait` parameters; only once the generic parameters start infecting struct fields and inference does `dyn Trait` earn its place, and even then hide it behind your own newtype (`struct DynDataAccess(Arc<dyn DataAccess>)`) so it can change later.
  Two consequences for the surface itself. **Smart pointers and wrappers do not belong in public signatures** — `pub fn process(data: Arc<Mutex<Shared>>) -> Box<Processed>` makes the caller adopt your internal representation, and if two crates disagree about the wrapper the mismatch is unresolvable; take `&T`/`&mut T`/`T` and keep the wrapper inside. The target is *ownership and synchronization* wrappers leaking out of an implementation — `Arc<Mutex<…>>`, `Rc<RefCell<…>>`, a `Box` used only to move a value. Deliberate **type erasure** is a different thing and is exempt: `Box<dyn Error>`, `Box<dyn Trait>`, and `Pin<Box<dyn Future<Output = T> + Send>>` are the only way to write those signatures, and wrapping them in a newtype for its own sake buys nothing. The idiomatic way for a heavyweight, shared service type to be passed around is not `Arc<Service>` at the callsite but a **`Clone` type wrapping `Arc<Inner>`**: `#[derive(Clone)] pub struct Service { inner: Arc<Inner> }` with methods forwarding to `inner`, so users clone a cheap handle and never see the pointer. **Type parameters should not visibly nest**: `Service<Backend>` is acceptable, `Service<Backend<Store>>` is not, and a service-like type users must *name* should not nest on its own volition at all. Containers (`List<T>`) must expose a parameter and are exempt; so, deliberately, are ecosystem-level designs like Bevy's ECS or `axum`'s handlers, where the type magic buys more than it costs — a high bar
- **API-19.** Accept the most general parameter type the function can work with. Two cases beyond `AsRef` (OWN-7): a function taking a range should take `impl RangeBounds<T>` rather than `Range<T>` — let alone hand-rolled `(low, high)` pairs or two separate arguments — so callers may write `f(1..3)`, `f(1..)`, or `f(..)`. And a function that needs to *read or write bytes* should be written **sans-io**: take `impl std::io::Read` / `impl std::io::Write` (or `futures::io::AsyncRead`/`AsyncWrite` where it must span async runtimes) instead of a `File`. `fn parse_data(file: File)` forces a caller holding a network payload or an in-memory buffer to write it to disk first; `fn parse_data(data: impl Read)` accepts files, sockets, stdin, `&[u8]`, and test fixtures alike, and makes the logic testable without touching the filesystem (TEST-33). Types performing continuous, runtime-specific I/O are a different problem — abstract the runtime instead
- **API-20.** A custom collection should implement the iterator traits `std` establishes, or it will not compose with anything. For a `Collection<T>` meant for third parties: `Iter<'_, T>`, `IterMut<'_, T>`, and `IntoIter<T>` types with `Iterator` impls; inherent `iter()` and `iter_mut()`; `IntoIterator` for `Collection<T>`, `&Collection<T>`, and `&mut Collection<T>` (all three — the reference impls are what make `for x in &c` work); `FromIterator` so `collect()` targets it; and `Extend`. Add `DoubleEndedIterator`, `ExactSizeIterator`, and `FusedIterator` where the semantics genuinely hold. Implement `size_hint()` on every iterator and implement it **truthfully** — callers size allocations from it (PERF-2), and `ExactSizeIterator` on an iterator whose length is not exact is a correctness bug, not an optimization

## Cognitive Load

- **CL-1.** *Retired* — folded into **READ-1** ("prefer clarity over cleverness").
- **CL-2.** *Retired* — folded into **READ-2** (named intermediate variables).
- **CL-3.** Avoid implicit assumptions — make preconditions explicit via types, asserts, or guard clauses rather than relying on undocumented invariants
- **CL-4.** Prefer familiar patterns over obscure language features — use well-known Rust idioms (`if let`, `match`, `?`) over exotic type-level programming unless the type-level approach provides compile-time safety guarantees that runtime checks cannot
- **CL-5.** Balance structural complexity with cognitive load — when the two conflict, use the decision heuristic below. Key distinction: **library code consumed by experts** can tolerate higher cognitive load; **application code with mixed-experience teams** should minimize it; **frequently modified code** should always minimize cognitive load regardless of audience

### Cognitive Load Decision Heuristic

Weigh these five factors:

1. **Change frequency**: high-churn code → lower cognitive load (more readers over time)
2. **Audience expertise**: mixed team → explicit patterns; experts-only library → idiomatic/terse acceptable
3. **Correctness criticality**: safety-critical → prefer explicit for clarity even at higher structural cost
4. **Team familiarity**: well-established team idioms (iterator chains, phantom types) can have higher cognitive load
5. **Domain complexity**: complex domains → reduce incidental complexity to preserve capacity for essential complexity

Default: prefer reducing cognitive load. Accept higher cognitive load for library code consumed by experts or correctness-critical paths where explicitness would obscure invariants. Application code should almost always minimize cognitive load.

| Accept higher *structural* complexity for lower cognitive load | Accept higher *cognitive* load for lower structural complexity |
|---|---|
| Intermediate variables for clarity (even if +5 lines) | Familiar iterator chains (idiomatic Rust) |
| Explicit loops over clever combinators (when >3 steps) | Type-level programming (encodes invariants) |
| Early returns / guard clauses (even if +branches) | Combinator patterns (`and_then`, `map_or_else` — safer than explicit control flow) |
| Type states (even if +types/traits) | Phantom types (compile-time guarantees) |

### Refactoring Patterns

When flagging complexity or readability issues, suggest concrete refactoring:

- **Deep nesting** → early returns + guard clauses + extract to named functions; flatten `if let Some(x) = ... { if let Some(y) = ... { } }` chains into sequential let-else guards
- **Complex boolean logic** → extract named predicates: `let is_eligible = has_permission && !is_expired && meets_threshold;`
- **Long parameter lists** → group into config/options struct or builder pattern; `fn connect(opts: ConnectionOpts)` instead of 6 positional args
- **Nested matches** → simplify with combinators: `opt.as_ref().map(|v| v.field)` instead of `match opt { Some(v) => Some(v.field), None => None }`
- **Macro overuse** → prefer traits over macros for better error messages, IDE support, and type checking; macros are justified for boilerplate reduction when trait-based approaches would require significantly more code (e.g., derive macros, declarative test generators) — see also TRAIT-8
- Long functions → extract helpers; split by responsibility; one abstraction level per function
- Tight coupling → introduce traits or interfaces; push logic behind abstractions
- Large module → split by responsibility; keep public API in one place
