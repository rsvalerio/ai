# ASYNC rules

## Async (typical severity: Medium--High)

> ASYNC rules assume **tokio** as the async runtime. If the project uses a different runtime (e.g., `async-std`, `smol`), adapt API references accordingly.

- **ASYNC-1.** `spawn_blocking` for CPU-heavy work
- **ASYNC-2.** *Retired.* Channel selection is owned by **CONC-8**. For async-vs-sync `Mutex` choice, use `parking_lot::Mutex` / `std::sync::Mutex` when the critical section is short and never crosses `.await`; reach for `tokio::sync::Mutex` only when you must hold the guard across `.await` (see CONC-2)
- **ASYNC-3.** Bounded channels for backpressure (see also CONC-8 for detailed guidance)
- **ASYNC-4.** Batch small, fast-completing tasks (e.g., individual DB row inserts) into fewer spawned futures to reduce scheduler overhead; do NOT batch operations that should run independently or have different cancellation requirements — batching unrelated work couples their failure modes. The general target is *items per CPU cycle*, not per-item latency: partition work into chunks up front, let each task own its slice, and prefer batched APIs where the peer offers them (a single multi-row insert over a row-at-a-time loop, one publish of N messages over N publishes). Two shapes to flag as the inverse of this rule: **hot-spinning** a receiver or an atomic to shave latency off individual items — sleep or yield instead (ASYNC-8) — and work-stealing or rebalancing individual items between workers, which spends more on coordination than the work is worth. Shared state is worth having only when the cost of sharing is below the cost of recomputing (CONC-1)
- **ASYNC-5.** `join_all`/`FuturesUnordered` over serial `.await` in loops. The same defect appears one level up in stream pipelines: `while let Some(x) = s.next().await { work(x).await }` and `.then(…)` run one item at a time regardless of how many are ready — use `futures::StreamExt::buffered` (ordered), `buffer_unordered` (completion order), or `for_each_concurrent` with an explicit concurrency limit, which doubles as the bound that keeps the fan-out from becoming unbounded (CONC-3, ASYNC-13). Two mechanics the fix depends on: all three live on `futures::StreamExt` only — `tokio_stream::StreamExt` has none of them, so a module importing that one must switch traits rather than add the second import (ASYNC-13 footgun 2) — and `buffered`/`buffer_unordered` require `Item: Future`, so the stream needs a `.map(work)` first: `s.map(work).buffer_unordered(16)`. `for_each_concurrent(16, work)` takes the closure directly and needs no `.map`. The rewrite is only correct where the per-item work is **independent**: if items share ordering — a sequence applied to the same aggregate, writes whose order is observable downstream, an item whose input depends on the previous item's result — overlapping them changes behaviour, and the serial `.await` in the loop is the right shape. Do not read `buffered` as the safe middle ground: it preserves the order of the *results*, not serial execution, so up to `n` items still run at once and any order-sensitive side effect they perform is just as interleaved as under `buffer_unordered`. Establish independence before filing this as a finding
- **ASYNC-6.** Timeouts + retries + exponential backoff for all external calls. Pattern: wrap with `tokio::time::timeout(dur, fut).await` → on timeout, retry with exponential backoff (`delay * 2^attempt`, cap at max). Use `tokio-retry` crate for production retry logic; hand-roll only for simple cases. Always set a max retry count to avoid infinite loops. Two details the shape of the return type makes easy to get wrong:
  - **The result nests.** `timeout(dur, fut)` yields `Result<T, Elapsed>` where `T` is the future's own output, so wrapping a fallible call gives `Result<Result<T, E>, Elapsed>` and needs both layers handled: `Ok(Ok(v))` success, `Ok(Err(e))` the operation failed, `Err(_)` it never finished. Collapsing them with `??` is fine *only* if the outer `Elapsed` is first mapped into a domain variant (`#[error("upstream timed out after {0:?}")] Timeout(Duration)`) — a bare `Elapsed` propagated to a caller says "deadline expired" with no indication of which deadline (ERR-2, ERR-4) (`Result::flatten`, stable since Rust 1.89, is defined only on `Result<Result<T, E>, E>` — both layers must carry the *same* error type, so it applies only in the narrow case where the inner future itself returns `Result<T, Elapsed>`. With any domain error inside, the outer `Elapsed` has to be mapped before the two layers can collapse at all; on a project whose MSRV predates 1.89 the method is not available regardless.)
  - **A timeout cancels, it does not roll back.** On expiry the inner future is dropped at whatever `.await` it was parked on; anything it had already done — rows written, messages published, files partly rewritten — stays done, and anything after that await never runs. Treat a timed-out external call as *unknown outcome*, not as failure: retrying it must be idempotent (idempotency key, conditional write, dedup on the consumer), and any cleanup that must happen has to run **outside the timed region** — on an explicit cleanup or shutdown path — because the code after the await will not run. Be precise about what `Drop` can carry here: the dropped future does run the `Drop` impls of everything it owns, but `Drop` is **synchronous and cannot await**, so it covers releasing a lock, closing a file descriptor, or restoring an in-memory flag, and it cannot cover anything that round-trips — releasing a distributed lease, a graceful client `drain()`, a compensating write, a final flush. Putting async cleanup in a `Drop` impl is not a lesser version of doing it properly; it silently does nothing (CONC-14 covers the same trap on the shutdown path).
- **ASYNC-7.** Use sync code when async adds no value. Async has overhead (future state machines, polling, context switching). Decision: use async for network I/O, concurrent operations, and event-driven flows; use sync for CPU-bound work (via `spawn_blocking`), simple sequential I/O, and operations that don't benefit from concurrency. An `async fn` that never yields is just overhead
- **ASYNC-8.** Insert `tokio::task::yield_now().await` in compute loops that run for more than ~1--5ms without an `.await` point, to avoid starving other tasks on the runtime; for longer compute (>5ms), prefer `spawn_blocking` (ASYNC-1). **Spacing, once you are yielding:** a yield is not free — task switching costs hundreds of nanoseconds plus the lost CPU caches — so the work between two yield points should be long enough that the switch is noise, and short enough that nothing else starves. **10--100µs of CPU-bound work between yields** is a reasonable starting band; a `yield_now().await` on every iteration of a tight loop is itself a performance defect. A loop whose per-iteration cost is unpredictable should ask the runtime instead of guessing — tokio exposes its cooperative budget under `tokio::task::coop` (check availability against the tokio version in `Cargo.toml`; the API moved and stabilized across recent releases). Note a loop that already awaits real I/O each iteration needs no explicit yield: those await points are the preemption
- **ASYNC-9.** Separate state from task logic; pass only what tasks need; minimal tokio architecture
- **ASYNC-10.** Prefer native `async fn` in traits (stable since Rust 1.75) over the `async-trait` crate. When callers need `Send`-bounded futures (common in multi-threaded tokio runtimes), use `#[trait_variant::make(Send)]` from the `trait-variant` crate to generate a `Send`-bounded variant — this preserves static dispatch and avoids the `Box<dyn Future>` allocation that `async-trait` introduces. Reach for `async-trait` only when you genuinely need `dyn Trait` object-safety that `trait-variant` can't yet provide (deeply heterogeneous collections of erased async trait objects)
- **ASYNC-11.** Use async closures `async || {}` with `AsyncFn`/`AsyncFnMut`/`AsyncFnOnce` traits (stable since Rust 1.85); check project MSRV before adopting. The hierarchy mirrors `Fn`/`FnMut`/`FnOnce` (`AsyncFn` ⊃ `AsyncFnMut` ⊃ `AsyncFnOnce`), so accept the least-restrictive bound a callee needs. **`Send` caveat:** the `AsyncFn`-family `Send`-bound story is still incomplete — when the returned future must be `Send` (e.g. `tokio::spawn` on a multi-threaded runtime), prefer an explicit `F: Fn(T) -> Fut, Fut: Future<Output = …> + Send + 'static` signature, or move owned captures into an `async move` block, rather than relying on `AsyncFn` to infer the `Send` bound. `AsyncFn` is the right default for single-threaded use and `Arc`-protected shared state (see also ASYNC-10 for the trait-method `Send` story via `trait_variant`)
- **ASYNC-12.** Prefer `std::pin::pin!` (stable since Rust 1.68) over `Box::pin` when a future only needs to be pinned for the current scope — it pins to the stack frame with no heap allocation. The common case is polling a future repeatedly across loop iterations of `tokio::select!`, which requires `&mut fut` and therefore a pinned future: `let fut = pin!(do_work()); loop { select! { r = &mut fut => …, _ = tick.tick() => … } }`. Reach for `Box::pin` only when the pinned future must outlive the scope or be stored in a struct/collection (`Vec<Pin<Box<dyn Future>>>`)
- **ASYNC-13.** `Stream` is the *asynchronous* `Iterator`, not a push-based inversion of it. Both are **pull**-based: `Iterator::next` returns `Option<Item>` and `Stream::poll_next` returns `Poll<Option<Item>>` — the only difference is that a stream may answer "not yet" (`Poll::Pending`) and register a waker rather than block the thread. The consumer still drives it; nothing is pushed at it. (The genuinely push-shaped counterparts are `Sink`, `tokio::sync::broadcast`, and callback registration — reach for those when the *producer* must drive.) Choose by **readiness, not by finiteness**: iterators can be infinite (`std::iter::repeat`, `successors`, `cycle`) and streams are frequently finite, so the deciding question is only whether producing the next item requires awaiting — sockets, channel receivers, paginated HTTP, `Interval` ticks yes; an in-memory `Vec` no (ASYNC-7). There is still no stable trait in `std` (`std::async_iter::AsyncIterator` is nightly-only as of Rust 1.98), so depend on `futures::Stream` / `tokio_stream`; prefer returning `impl Stream<Item = T>` from library APIs (the async counterpart of API-3) and build it with `async_stream::stream!` instead of hand-writing a `poll_next` state machine. Stream adapters are lazy exactly like iterator adapters — a `.map()` that is never polled to completion does no work (PERF-1). Because the consumer controls polling, a `Stream` *expresses* backpressure — but it only *applies* it when the source honours demand. A stream that produces items on demand (an `AsyncRead`, a paginated HTTP fetcher, `async_stream::stream!` awaiting its own work) genuinely throttles the producer by not being polled. A stream that merely *drains* something already filling up does not: `ReceiverStream` over an `mpsc::unbounded_channel`, a `BroadcastStream`, or any adapter over a buffer someone else writes to will let that buffer grow without limit no matter how slowly it is polled — the bound has to come from the channel (CONC-3, CONC-8), not from the stream in front of it. Check where the items are actually produced before treating a `Stream` as the pull-shaped alternative to an unbounded channel. **Three footguns:** (1) `StreamExt::next` requires `Unpin` — pin with `std::pin::pin!` before looping (ASYNC-12); (2) `futures::StreamExt` and `tokio_stream::StreamExt` are distinct traits with overlapping method names and *different signatures* (`futures`' `fold` takes an async closure, `tokio_stream`'s takes a sync one), so importing both yields ambiguity errors — pick one per module; (3) `futures::StreamExt` has no `sum`/`product` — use `fold`
- **ASYNC-14.** Async I/O does not turn end-of-file into "wait for more data". `tokio::fs::File` behind `BufReader::lines()` — or any `AsyncRead` — reports EOF and ends the loop exactly like its `std::fs` equivalent; `async` means the *thread* is not blocked while a read is in flight, not that the reader follows a file still being appended to. (Measured: a `tokio` line reader over a growing file terminates at the current EOF in ~250µs and never observes later appends.) Implementing `tail -f` requires an explicit strategy — re-poll after a delay on EOF while tracking byte offset and handling truncation and rotation (inode change), watch via `notify` (inotify/kqueue), or subscribe to the log transport rather than the file. Flag any "follow the log" loop that relies on async alone to block at EOF; it will exit on the first quiet moment and silently stop processing. Related trap: `tokio::io::Lines` is **not** a `Stream` — it exposes an inherent `next_line().await` returning `io::Result<Option<String>>`; wrap it in `tokio_stream::wrappers::LinesStream` (requires tokio-stream's `io-util` feature) to get `StreamExt` (ASYNC-13)
- **ASYNC-15.** Declare `async fn foo()` rather than `fn foo() -> impl Future<Output = …>` — it reads normally, needs no wrapping `async {}` block in the body, and is what callers expect. The exception is the reason to know the difference: **a future's size is the size of everything held across its `.await` points, plus everything passed into it**, and that whole state machine is memcpy'd when the future is boxed or handed to `spawn`. Locals that live only *between* two awaits stay on the thread stack; locals that straddle an await — including values that are merely still in scope for `Drop` — become fields of the future's type, as do all arguments, even ones the body never uses after the first await. On a future instantiated thousands of times a second this shows up as stack pressure and copy overhead. Track it where it matters with a test rather than by guessing: `let f = hot(); assert!(size_of_val(&f) < N);` — pick `N` from the first run and let it fail when the size regresses. The fixes, in order of how often they pay: shrink or box the types held across awaits; drop or scope large locals before the first await; and where arguments are the problem, move the setup out of the async body by returning `impl Future` from a plain `fn`, using `Either` (`futures`' `left_future()`/`right_future()`) when the two arms would otherwise be different anonymous types. Applies to hot paths only — for ordinary async code `async fn` is correct and the future size is irrelevant
- **ASYNC-16.** Every future in a `tokio::select!` arm must be cancellation-safe, and that is a per-method property you have to look up rather than infer. `select!` polls its branches and **drops** the futures of every branch that loses the race (CONC-14 notes the same drop on the shutdown path); a future is cancellation-safe when that drop loses no data and leaves no half-applied state. The distinction is not visible at the call site — `rx.recv()` and `stream.read_exact(&mut buf)` look identical in an arm, and only one of them is safe there.
  Cancellation-safe, so fine to write directly in an arm: `tokio::sync::mpsc::Receiver::recv`, `broadcast::Receiver::recv` (subject to the `Lagged` handling in CONC-8), `watch::Receiver::changed`, `Notify::notified`, `Semaphore::acquire` and `tokio::sync::Mutex::lock` (both hand out permits in request order, so cancelling only loses your place in the queue — a fairness and liveness cost under contention, not a correctness one), `JoinSet::join_next`, `StreamExt::next`, `tokio::time::sleep`/`interval.tick`, and `mpsc::Sender::send` — though note precisely what "safe" buys you for `send`: tokio guarantees the message was *not* sent, and the value was moved into the future, so dropping the losing branch **drops the message with it**. Cancellation-safe here means the channel is left consistent, not that delivery is retryable — the safe list answers ASYNC-16's question, not the separate question of whether a cancelled operation can be re-attempted. Where the message must survive losing the race, acquire capacity before selecting rather than after: `let permit = tx.reserve().await?;` outside the `select!`, holding it across the selection so the arm's `permit.send(msg)` can neither block nor fail; where that does not fit, clone the value before the arm or hand the send to a dedicated task (fix 2 below). Not cancellation-safe: `AsyncReadExt::read_exact`, `read_to_end`, and `read_to_string` (bytes already read are dropped with the future — the stream is left mid-message and every later read is misaligned), `AsyncWriteExt::write_all` (an arbitrary prefix has been written), and any future of your own that mutates shared state between two `.await`s. Anything wrapping non-cancellation-safe work inherits the property.
  Two fixes, in order: (1) hoist the future out of the `select!` so cancellation cannot drop it mid-flight — `let fut = pin!(read_frame(&mut sock)); loop { select! { r = &mut fut => …, _ = token.cancelled() => … } }` resumes the *same* future each iteration instead of starting a new one (ASYNC-12 has the pinning mechanics); (2) move the operation into its own task and select over a channel or `JoinHandle`, which are cancellation-safe — with one mechanic to get right: await the handle **by mutable reference** (`res = &mut handle => …`), because a `JoinHandle` written by value is *moved into the arm and dropped* when that branch loses, and dropping a tokio `JoinHandle` detaches the task rather than aborting it. The work then keeps running with nothing left to await and its result discarded — fine when detaching is what you meant, a leak when it was not. Where losing the race must actually stop the operation, keep the handle, call `handle.abort()`, and await it to observe the `JoinError`; where several such tasks are supervised together, `JoinSet` owns them and `shutdown()` aborts the set (CONC-14). Writing the state-restoring code by hand is not a third option: `Drop` is synchronous and cannot await, so nothing that round-trips can be undone there (ASYNC-6).
  **Scan signal:** a `select!` arm calling `read_exact`, `read_to_end`, `read_to_string`, `write_all`, or a project-local `async fn` that performs more than one awaited step — and, in the loop form, one of *those* futures constructed inside the arm rather than pinned outside the loop, which silently restarts it after every iteration. Constructing a future in an arm is not itself a finding: `rx.recv()` or `sleep(d)` written directly in a loop's arm is the idiomatic spelling, because restarting a cancellation-safe future costs nothing
