# CONC rules

## Concurrency (typical severity: High--Critical)

- **CONC-1.** Choose the right shared ownership primitive: `Arc<T>` for immutable shared state; `Arc<RwLock<T>>` when reads dominate and writes are rare; `Arc<Mutex<T>>` for occasional writes; almost never `Mutex<Arc<T>>` (rare exception: atomically swapping the inner `Arc`). **Read-mostly *whole-value* state is a distinct case** worth separating out: config snapshots, routing tables, feature flags, allowlists, certificate bundles — read on nearly every request, replaced wholesale and rarely. `Arc<RwLock<T>>` makes every reader participate in locking for data that almost never changes; `arc_swap::ArcSwap<T>` gives lock-free reads (`.load()` hands back a guard to the current `Arc`) while writers publish a new version with `.store(Arc::new(next))`. The trade-off is that an update *replaces* the value rather than mutating it in place — which is exactly right for configuration (immutable snapshots, atomic publication, no half-updated state) and wrong for state that must be edited field-by-field. In async code that also needs *change notification*, prefer `tokio::sync::watch` (CONC-8): it covers latest-value broadcast and lets receivers await updates. Reach for `ArcSwap` when readers only ever sample the current value, including from sync code
- **CONC-2.** Hold locks briefly; never across `.await`
- **CONC-3.** Prefer channels over shared state; bounded channels provide natural backpressure. Capacity sizing has no universal constant — it is a function of the producer/consumer rate gap and the acceptable queueing latency. Default to a small capacity (4--32) and tune from telemetry (observed queue depth, producer wait time, end-to-end latency). Red flag: unbounded channels in production — they defer OOM to runtime instead of surfacing backpressure
- **CONC-4.** `tokio::select!` for cancellation/timeouts; common patterns: (1) shutdown signal: `tokio::select! { _ = shutdown.recv() => break, msg = rx.recv() => handle(msg) }`, (2) timeout: `tokio::select! { result = work() => result, _ = tokio::time::sleep(dur) => Err(Timeout) }`
- **CONC-5.** Never block in async — common offenders and their async equivalents: `std::thread::sleep` → `tokio::time::sleep`, `std::fs::{read,write,rename,remove_file,create_dir_all,File::create,metadata,exists}` → `tokio::fs::*`, `std::net::TcpStream` → `tokio::net::TcpStream`, synchronous `reqwest::blocking` → `reqwest` async client; for unavoidable blocking (e.g., CPU-heavy compute, blocking C library, sync sqlite/rusqlite calls), use `spawn_blocking` (ASYNC-1). **Checklist for `cli::commands::bench` and `bench::runner`: any `std::fs::*` or sync store call inside an `async fn` is a defect** — either swap to `tokio::fs` or move the block under `tokio::task::spawn_blocking`
- **CONC-6.** Structured concurrency: `JoinSet` for task groups — ensures all spawned tasks are tracked, awaited, and cleaned up; prevents orphaned tasks that silently leak resources or panic. Drop a `JoinSet` to cancel all tasks in the group. Prefer `JoinSet` over ad-hoc `Vec<JoinHandle>` + `join_all` for dynamic task groups
- **CONC-7.** Avoid `Mutex` around collections (`HashMap`, `VecDeque`, `Vec`) in hot paths; prefer `DashMap` (sharded `RwLock`s), `crossbeam::queue`, or manual sharding for high-contention scenarios; for simple patterns, evaluate `std::sync::mpsc` (reworked in Rust 1.67 to be crossbeam-based) before pulling in external crates
- **CONC-8.** Channel type selection:

  | Channel | Context | Use case |
  |---|---|---|
  | `crossbeam::channel` | Sync | Select, bounded with backpressure, multi-producer |
  | `tokio::sync::mpsc` | Async | Point-to-point message passing |
  | `tokio::sync::broadcast` | Async | Fan-out / pub-sub (multiple receivers) |
  | `tokio::sync::oneshot` | Async | Single request-response or completion signal |
  | `tokio::sync::watch` | Async | Latest-value broadcast (config updates, state) |

  Rule of thumb: `crossbeam` for sync code needing `select!` or bounded backpressure; `tokio::sync` for async code — it integrates with the runtime. Backpressure, though, is a property of the *individual* channel, not of the crate: bounded `crossbeam::channel` provides it on the sync side, and among the tokio async channels **only bounded `mpsc::channel(n)` does**. Pick deliberately: **bounded `mpsc::channel(n)`** applies real backpressure, because `send().await` parks the producer once the buffer is full; **`mpsc::unbounded_channel()`** has a non-async `send` that never waits for capacity, so it applies none and grows until memory runs out (CONC-3 — this is the unbounded-queue red flag, and reaching for it to "fix" a slow consumer converts backpressure into an OOM). Note that "never waits" is not "never fails": unbounded `send` still returns `Result<(), SendError<T>>` and errors once every receiver is dropped or closed (verified), so the value is handed back exactly as with the bounded sender — what it never does is *slow the producer down*. **`broadcast::channel(n)`** is a bounded **ring buffer** that does not block the sender at all — when a receiver falls behind, the oldest messages are overwritten and that receiver is told after the fact via `Lagged(n)` (see below). `BroadcastStream` inherits exactly this: wrapping it in a `Stream` does not add backpressure (ASYNC-13). So bounded `mpsc` slows the producer down, `broadcast` drops data instead, and unbounded `mpsc` does neither.

  **Failure shapes differ per channel, and only one of them is "the receiver went away".** Do not write generic "sends and receives can fail, handle them" code — check the actual signature:

  | Operation | Returns | Failure means |
  |---|---|---|
  | `mpsc::Sender::send` | `Result<(), SendError<T>>` | the receiver is gone — either dropped **or still alive but explicitly closed** via `Receiver::close()`. **The unsent value is returned inside the error** (`e.0`), so it can be re-routed, persisted, or counted rather than dropped |
  | `mpsc::Receiver::recv` | `Option<T>` — **not** a `Result` | `None` = no more messages will arrive and the buffer is drained: either every sender dropped, **or the receiver called `close()`**, which stops new sends while still yielding what is already buffered. Normal termination either way, and `while let Some(x) = rx.recv().await` handles it |
  | `oneshot::Receiver` (awaited) | `Result<T, RecvError>` | the sender was dropped without sending — usually a task that panicked or returned early |
  | `broadcast::Receiver::recv` | `Result<T, RecvError>` | `Closed` = all senders gone; **`Lagged(n)` = this receiver fell `n` messages behind and those messages are gone** |
  | `watch::Receiver::changed` | `Result<(), RecvError>` | sender dropped; note `watch` conflates intermediate updates by design — only the latest value is observable |

  `broadcast::error::RecvError::Lagged(n)` is the dangerous one: it is **silent data loss reported as an error**, and `recv()` resumes from the oldest retained message afterwards rather than failing permanently (verified: capacity 4, 10 sends, first `recv()` returns `Lagged(6)` then yields message 6). Code that `?`s it away, or logs it and continues, has just dropped `n` messages from an audit trail, a replication feed, or a cache-invalidation stream while reporting healthy. Flag any `broadcast` consumer that does not treat `Lagged` distinctly from `Closed` — the correct responses are to increase capacity, resynchronize from the source of truth, or fail the consumer loudly, and `n` should be a metric
- **CONC-9.** Understand lock-free trade-offs: CAS retry loops can spin under high contention (many threads competing on the same atomic variable), wasting CPU cycles and potentially performing worse than a `Mutex` under sustained contention; profile with realistic concurrency levels before assuming lock-free is faster — measure both throughput and tail latency
- **CONC-10.** For lazily-initialized global/static state, prefer `std::sync::OnceLock<T>` (stable since 1.70) and `std::sync::LazyLock<T>` (stable since 1.80) over the `once_cell` crate and the legacy `lazy_static!` macro. `OnceLock` for manual initialization, `LazyLock` for closure-based initialization. `once_cell`/`lazy_static` remain acceptable for MSRV <1.80 only — for new code at modern MSRVs, flag as an EFF finding.

  **Separately, a library should not put *correctness-relevant* state in a `static` or `thread_local!` at all**, whatever the initialization mechanism. Cargo may link several major versions of the same crate into one binary (`0.4` and `0.5` are distinct majors), and each linked copy gets its **own** instance of every static — so a counter, registry, cache, or global config in `core 0.4` is a *different* variable from the one in `core 0.5`, and two dependencies that both "increment the global counter" silently update two counters. The same duplication happens per dynamic library (SEC-40). Statics also break test isolation (TEST-18) and become a contention point in thread-per-core designs. Statics used purely as an optimization — a memoized lookup table, an interned-string cache — are fine, because a duplicated copy is still correct. Anything whose value being silently duplicated would be a bug belongs in a value the caller owns and passes in
- **CONC-11.** `thread_local!` for genuinely per-thread state (scratch buffers, per-thread RNG, sync-code context) — each thread gets an independent instance, so no lock is needed. Use the `const { }` initializer (stable since Rust 1.59) when the initial value is const-evaluable: `thread_local! { static BUF: RefCell<Vec<u8>> = const { RefCell::new(Vec::new()) }; }` — it skips the lazy-init check on every access. **Async footgun (flag as a defect):** a tokio task is not pinned to a worker thread — it can resume on a different thread after any `.await`, so a `thread_local!` read before an `.await` and after it may hit different values. Never use `thread_local!` to carry per-*task* context in async code; use `tracing::Span`, `tokio::task_local!`, or an explicit context parameter instead. Also note `thread_local!` destructors do not run for threads that are never joined (including the process exit path), so do not rely on them for flushing or cleanup
- **CONC-12.** Pad independently-written shared state to a cache line with `#[repr(align(N))]` (stable since Rust 1.25) to avoid **false sharing** — two atomics or counters that live in one cache line force the cores writing them to bounce that line back and forth, so throughput collapses even though the values are logically unrelated. The classic shape is a per-worker stats array: `struct Counters([AtomicU64; N])` where every worker hammers its own index and all of them share a line. Prefer `crossbeam_utils::CachePadded<T>` over hand-rolled alignment — it already encodes the per-architecture line size, which is **not** universally 64 bytes (128 on x86-64 and aarch64 because of adjacent-line prefetch, 32 on some embedded targets); a hardcoded `align(64)` is wrong on exactly the platforms where the problem is worst. Costs memory proportional to the padding, so apply it to hot per-worker state, not to every struct with an atomic in it, and confirm with a profiler that the line is actually contended. Alignment beyond this — SIMD operands, DMA buffers, hardware-mandated layout — is a low-level concern outside these rules
- **CONC-13.** A spawned task's failure does not reach anyone unless something joins it. **This rule describes the default `panic = "unwind"` strategy**; under `panic = "abort"` (set in a `[profile.*]`, common in embedded and size-tuned release builds) there is no unwind to catch, so the first panic in any task takes the whole process down immediately — verified: with `panic = "abort"` the `JoinHandle` is never resolved and no line after `h.await` runs, whereas the same binary under unwind reports `is_panic=true` and exits 0. Check the profile before relying on either behaviour; abort turns every task panic into a crash, which is louder but removes the option to supervise.

  Under unwind, `tokio::spawn` catches the unwind and stores the outcome in the `JoinHandle`; drop the handle (or never await it) and the task's panic disappears from the program's control flow. It is not *silent* — the default panic hook still writes `thread 'tokio-rt-worker' panicked at …` to stderr — but nothing else happens: the runtime keeps going, the supervising task never learns the work stopped, and **the process still exits 0** (verified on tokio 1.53). A background flusher, reconciler, or metrics exporter that dies this way leaves a service that looks healthy and has silently stopped doing one of its jobs. Await the handle, or hold tasks in a `JoinSet` (CONC-6) and drain `join_next()`. When you do handle the error, `JoinError` is **not** synonymous with panic — the common `eprintln!("Task panicked: {e:?}")` handler mislabels every cancellation:
  - `e.is_panic()` — the task panicked; `e.into_panic()` returns the payload and lets you `std::panic::resume_unwind` to propagate the failure into the parent.
  - `e.is_cancelled()` — the task was `abort()`ed or its `JoinSet` was dropped. During shutdown this is the expected path and must not be logged as an error (CONC-14).

  Detached tasks are legitimate for genuinely fire-and-forget work, but the choice must be deliberate: if the task's failure would matter to anyone, it needs a supervisor — a `JoinSet`, a restart loop, or at minimum a `tokio::spawn(async move { if let Err(e) = handle.await { … } })` that turns the `JoinError` into a metric and a structured log (READ-8). Setting a process-wide `std::panic::set_hook` that aborts is the blunt alternative when any task panic should take the service down; do it deliberately, not as a substitute for supervision
- **CONC-14.** Graceful shutdown means the signals the platform actually sends. `tokio::signal::ctrl_c()` alone listens for **SIGINT only**; a container runtime, Kubernetes, and systemd all stop a process with **SIGTERM**, whose default disposition is immediate termination — so a service whose shutdown path is `ctrl_c().await` dies instantly on every real deployment restart and runs none of its cleanup. Verified: a process awaiting only `ctrl_c()` and sent SIGTERM exits before the line after the await. Note the SIGKILL that follows in the orchestrator's sequence is *not* what killed it: SIGKILL is sent only if the process is **still alive** when the grace period expires, which is the failure mode of a service that does trap SIGTERM but drains too slowly (see "Bound the drain" below). An untrapped SIGTERM is already fatal on its own. Handle both signals, and on Unix add SIGHUP if the process is not using it for reload:

  ```rust
  use std::time::Duration;

  use anyhow::{Context, Result};
  use tokio::runtime::Runtime;
  use tokio::signal::unix::{signal, Signal, SignalKind};

  /// Install at startup, before serving traffic, so a registration failure is a
  /// startup error with context rather than a surprise during shutdown.
  fn install(kind: SignalKind, what: &'static str) -> Result<Signal> {
      signal(kind).with_context(|| format!("installing {what} handler"))
  }

  async fn shutdown_signal(int: &mut Signal, term: &mut Signal) {
      tokio::select! { _ = int.recv() => {}, _ = term.recv() => {} }
  }

  // Not `#[tokio::main]`: `shutdown_timeout` takes `self`, so the runtime has to be
  // an owned value here for the "Bound the drain" step below to be available at all.
  fn main() -> Result<()> {
      let rt = Runtime::new().context("building the tokio runtime")?;
      rt.block_on(async {
          // Both fail fast, before anything is served.
          let mut int = install(SignalKind::interrupt(), "SIGINT")?;
          let mut term = install(SignalKind::terminate(), "SIGTERM")?;
          // … start the service …
          shutdown_signal(&mut int, &mut term).await;
          // … cancel, then drain — both handlers are still alive here, so a second
          //     interrupt during the drain is observable rather than swallowed …
          Ok::<(), anyhow::Error>(())
      })?;
      // Bound how long teardown blocks; see "Bound the drain" below for what it does not do.
      rt.shutdown_timeout(Duration::from_secs(5));
      Ok(())
  }
  ```

  **Why the interrupt handler is a long-lived `Signal` and not `tokio::signal::ctrl_c()` inside the `select!`.** Two reasons, and the second is the one that bites. First, `ctrl_c()` returns `io::Result<()>`, so a `select!` arm written `_ = tokio::signal::ctrl_c() => {}` discards a registration error that should have been a startup failure. Second, losing the `select!` race **drops** that future — and tokio's process-wide SIGINT handler stays installed, so SIGINT is thereafter neither delivered to a listener nor fatal. Verified: after a SIGTERM won the race, a SIGINT sent during the drain was silently swallowed and the process drained to completion as if nothing arrived. That is the opposite of what an operator hammering Ctrl-C through a slow shutdown expects. Holding both `Signal` streams in `main` keeps them registered for the whole shutdown, which is what makes "press Ctrl-C again to give up on the drain" implementable at all (verified: the second interrupt is observed). `tokio::signal::ctrl_c()` remains the right portable spelling for the simple case — a one-shot wait that is never raced and never needed again — and on Windows it is the only spelling.

  `tokio::signal::unix` is `cfg(unix)` and needs tokio's `signal` feature; on Windows the counterparts are `signal::windows::{ctrl_c, ctrl_shutdown, ctrl_close}`. Three further requirements, each of which is a separate finding when missing:
  - **Propagate, don't just observe.** Receiving the signal in `main` does nothing for tasks already running. Broadcast it *cooperatively*, so each task reaches its own safe stopping point: `tokio_util::sync::CancellationToken` (`token.cancelled()` in a `select!` arm on every long-lived task) or a `watch::Sender<bool>`. CONC-4 has the `select!` shape. Note `JoinSet::shutdown()` is **not** in this list — it aborts, which is the force-quit step below, not a way to ask tasks to wind down.
  - **Bound the drain.** Wrap the "wait for in-flight work" phase in `tokio::time::timeout`; an unbounded drain converts a graceful shutdown into a hang that the orchestrator resolves with SIGKILL anyway. Size the deadline below the platform's grace period (Kubernetes `terminationGracePeriodSeconds`, default 30s). Only *after* that deadline expires does force-abort apply — `JoinSet::shutdown()` (abort every task and await it) or `handle.abort()` per task — and everything under "Release externals" about what abort skips applies to whatever it catches mid-flight.

    **The force path is not itself bounded, because `spawn_blocking` work cannot be aborted once it has started** (tokio 1.53.1). `abort()` on a running blocking task returns immediately and does nothing: measured, the call took ~1.5µs, the closure ran to completion, and `handle.await` returned **`Ok(value)`** — not even a `JoinError`, so a supervisor checking `is_cancelled()` sees a clean success. `JoinSet::shutdown()` inherits this and simply waits: with one 3s blocking task in the set it took 2.7s to return, versus ~0.5ms to abort an equivalent async task. A force-abort step assumed to be instant therefore blows straight through the drain deadline and into the platform's grace period, which is the SIGKILL the deadline existed to avoid. Keep blocking work off this path entirely: give long `spawn_blocking` closures a cooperative cancellation flag they poll between chunks (an `AtomicBool`, a `CancellationToken` checked with `is_cancelled()`), and bound the runtime teardown separately with `Runtime::shutdown_timeout` so the *wait* ends on a deadline you chose rather than one the orchestrator chose (verified: returned in 1.0005s against a 10s blocking task). Be precise about what that buys, because the name oversells it: **it stops waiting; it does not stop the work.** A `spawn_blocking` closure that has already started is not terminated and its thread is not killed — it is merely no longer awaited, and it keeps running until it returns, still holding whatever it holds and still performing whatever it does. Verified: with the runtime dropped after a 1s `shutdown_timeout`, an abandoned closure went on to complete two seconds later and write its output file. So a connection, lock, temp file, or partial write owned by that closure outlives "shutdown complete", and any side effect it has left to perform will still land — possibly after the code that was supposed to flush and close things has finished. Treat `shutdown_timeout` as a bound on how long you *block*, and cooperative cancellation as the only thing that bounds what actually *runs*. Note it also takes `self`, so it is unavailable under `#[tokio::main]`; what it requires is an *owned* runtime, which either `Runtime::new()` or `runtime::Builder` provides — reach for the builder only when you also need to configure worker threads, names, or timers. Keep that value in `main` so there is something to call `shutdown_timeout` on. Chunk the work finely enough that the poll interval fits inside the drain budget — a closure that checks a flag once every 30s is not cancellable in any way that matters.
  - **Release externals explicitly.** Connection pools, NATS clients (NATS-7 `drain()`), open writers, and in-memory buffers need flushing on this path. Aborting a task *does* run `Drop` — the future is dropped at its current await point, destroying owned locals and task-local values in scope (verified on tokio 1.53) — but `Drop` is synchronous, so it cannot await. Anything whose release is itself an async operation (a NATS `drain()`, a graceful connection close, a final flush that round-trips) will not happen, and neither will any code positioned *after* the await the task was parked on. Cleanup that must be awaited belongs on the shutdown path itself — signal the task, then let it finish — not in a `Drop` impl and not after the await of a task you are about to abort.

  Note what the example does *not* do: `signal()` returns `io::Result<Signal>`, and `.expect()` on it is an ERR-5 finding in a long-running service. Failing to install a SIGTERM handler is worth refusing to start over — but as a propagated startup error carrying context (ERR-4), surfaced before the process accepts traffic, not as a panic buried in a shutdown helper that runs an hour later. Registering at startup rather than at shutdown is the point: a handler installed lazily on the shutdown path can fail at the one moment there is no longer anywhere to report it
- **CONC-15.** For parallelism that ends inside the current function, `std::thread::scope` (stable since Rust 1.63) lets the spawned threads borrow local data directly — no `Arc`, no `clone`, no `'static` bound, and the scope joins every thread before it returns, so a forgotten handle is not a leaked thread (CONC-6 is the async analogue). `thread::spawn` requires `'static` because the thread may outlive the caller; `scope` removes that requirement by removing the possibility. Reach for it in place of the reflexive `Arc<Mutex<T>>` + `join` when the work is a bounded fan-out over data the caller already owns: `thread::scope(|s| { for chunk in data.chunks(n) { s.spawn(move || process(chunk)); } })` (each closure must `move` its own chunk — a borrow of the loop variable does not live for the scope) — disjoint `&mut` chunks via `chunks_mut` need no lock at all (OWN-13 is the same disjointness argument at the field level). Two caveats: a panic in a scoped thread is re-raised in the parent when the scope joins, which is usually what you want but means the scope is a panic point; and `scope` blocks the calling thread until every child finishes, so it must not be called from an async context (CONC-5) — wrap it in `spawn_blocking`.
