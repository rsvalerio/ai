# ARCH rules

## Architecture & Modules

- **ARCH-1.** No god objects or god modules; split by responsibility. Module-level red flags: >500 lines, mixed unrelated concerns (e.g., parsing + networking + serialization in one file), >10 public items with no cohesive theme
- **ARCH-2.** At module boundaries, depend on traits for decoupling and testability; within a module, start concrete until abstraction is justified (see TRAIT-9 for when to extract traits)
- **ARCH-3.** Modules by concern (`auth`, `db`, `error`), not layer — anti-pattern: `models/`, `controllers/`, `services/` directories that scatter a single feature across many folders; instead, group by domain so related types, logic, and tests live together. Module *layout* follows the same logic as menu design: the handful of items a user must find to use the crate at all belong in the **root** (a `foo_client` crate's `Client`), and everything else groups into submodules named for the use case — `account`, `network`, `status`, never `traits`, `errors`, or `types`, which sort items by what they are rather than what they are for. Both extremes are findings: a flat root of dozens of unordered public items, and a root with nothing in it behind a wall of submodules. (Generated `-sys` crates and genuine umbrella crates are the exceptions.) Submodules are also where subsystem-level documentation belongs (API-14)
- **ARCH-4.** Shared code used by multiple concerns should be organized as its own concern-named module (e.g., `crypto`, `field_path`, `json_fields`) rather than generic buckets like `helpers`/`utils`. Cross-module dependencies are normal; keep them explicit, one-directional, and keep public API re-exports curated in `lib.rs`. If the code is purely implementation detail, prefer an `internal` module with descriptive submodules over a grab-bag utility module.
- **ARCH-5.** High cohesion within modules; no circular dependencies
- **ARCH-6.** Match abstraction to problem complexity; YAGNI. **Prefer deferring the abstraction to guessing at it**, because the information needed to pick the right one arrives after the code is written, not before: refactoring a simple, concrete implementation is easy and available to anyone, while refactoring a wrong abstraction is neither, and the wrong one actively hides the better decomposition underneath it. The classic shape is a data pipeline made format-generic on the theory that a second format will be needed, which locks in a `Format` trait that never gains a second impl and obscures the split that would actually have helped (validation from export). Repetition, not anticipation, is the signal to abstract — when the same shape appears a third time, the pattern is being shown to you rather than predicted (DUP-1--10); and attempting an abstraction, finding it does not fit, and reverting to the concrete version is a successful outcome, provided the finding is written down. Two litmus tests for whether the abstraction landed: **adding the next feature feels obvious** — there is one place it goes, no conversion glue between layers, and testing needs no elaborate mocking (TEST-33); and **the doc comment says "X" rather than "X and Y"** — a type whose summary needs an "and" is two types (ARCH-1, FN-6). Speculative flexibility ("we might need to swap the database") is the specific claim to challenge in review: ask which caller needs it *in this change*
- **ARCH-7.** Prefer flat file layout (e.g., `foo.rs` + `foo/bar.rs`) over `mod.rs` for new code; both are idiomatic — follow project convention when one exists
- **ARCH-8.** `lib.rs` = thin entry point: module declarations, re-exports, crate-level docs, and small central types only. Move out: error types (→ `error.rs` when >50 lines or shared across modules), implementation logic, private helpers, domain logic. Organization heuristic: inline error types for ≤2 types in ≤50 lines; when types exceed ~50 lines or you have 3+ helper functions, extract to a dedicated module
- **ARCH-9.** Minimal public surface; hide internals behind modules
- **ARCH-10.** Snake_case files; singular names (`config.rs` not `configs.rs`)
- **ARCH-11.** In Cargo workspaces, centralize shared dependency versions and lints in `[workspace.dependencies]` and `[workspace.lints]`, then inherit with `dep = { workspace = true }` and `[lints] workspace = true`. Prevents version drift across member crates and makes CVE upgrades a single-point change. Flag workspaces where sibling crates pin different versions of the same transitive dep or duplicate lint configuration. Three details that make this actually hold: (1) declare **every** dependency in `[workspace.dependencies]`, including ones only a single crate uses, so there is one place to audit; (2) declare them with `default-features = false` and let members opt into the features they need, since a workspace-level feature is silently unified into every member (ARCH-12); (3) **workspace members are dependencies too** — `sibling = { path = "crates/sibling", version = "0.5.2" }` in `[workspace.dependencies]` with `sibling.workspace = true` in the member, not a bare `sibling.path = "../sibling"` in each crate, which publishes unversioned and resolves inconsistently.
  `[workspace.lints]` is also where the project's static-verification policy lives, and an empty one is a finding on its own. A reasonable baseline turns on the compiler lints that are off by default (`missing_debug_implementations`, `unsafe_op_in_unsafe_fn`, `unused_lifetimes`, `redundant_lifetimes`, `redundant_imports`, `trivial_numeric_casts`, `ambiguous_negative_literals`) and the major clippy groups (`correctness`, `suspicious`, `complexity`, `perf`, `style`, `pedantic`, `cargo`) at `warn` with `priority = -1`, plus a few `restriction` lints that pay for themselves — `undocumented_unsafe_blocks` (UNSAFE-1), `allow_attributes_without_reason` (READ-10), `unused_result_ok`, `map_err_ignore`, `clone_on_ref_ptr`, `dbg_macro` (READ-9). Opt back out case by case rather than not enabling them. A project handling untrusted input should weigh a **second restriction tier** that the pedantic group does not cover: `indexing_slicing` (ERR-16), `join_absolute_paths` (SEC-14), `unchecked_duration_subtraction` (TIME-3), `integer_division`, and — where the crate is not arithmetic-heavy — `arithmetic_side_effects` (SEC-15). Be honest about the cost when recommending these: they are `restriction` rather than `correctness` precisely because they fire on correct code as readily as on wrong code, so adopt them per-crate at `warn` and silence the provably-fine sites with scoped `#[expect(…, reason = "…")]` (READ-10), never crate-wide at `deny` (ARCH-18). Beyond lints, CI should carry `cargo audit` (SEC-27), `cargo-udeps` for dependencies nothing imports, `cargo-hack` to prove the feature combinations actually build (ARCH-12), and `cargo miri test` where the crate has `unsafe` (UNSAFE-10)
- **ARCH-12.** Enforce feature-flag invariants with `compile_error!` rather than a runtime check or a silent fallback. Cargo features are *additive* — any consumer in the dependency graph can turn one on, and `--all-features` turns on every one — so a crate whose backends are mutually exclusive, or that requires at least one of a set, must say so at compile time:

  ```rust
  #[cfg(not(any(feature = "sqlite", feature = "postgres")))]
  compile_error!("enable exactly one backend: `sqlite` or `postgres`");
  #[cfg(all(feature = "sqlite", feature = "postgres"))]
  compile_error!("`sqlite` and `postgres` are mutually exclusive");
  ```

  Cover both directions (none-selected *and* over-selected); a single `not(any(...))` guard still lets `--all-features` produce a nonsense build. Prefer restructuring so features are genuinely additive (e.g. select the backend at runtime from a trait object) — mutually exclusive features are a design smell that breaks feature unification for downstream crates. Additive means, concretely: enabling a feature may add public items but must never **remove or change** one (adding enum variants is fine only behind `#[non_exhaustive]`, API-9); a feature must not require the user to also enable another one by hand; a feature must not depend on its parent *not* enabling something in a child; and there is no such thing as a `no-std` feature — invert it into a `std` feature, because `--all-features` and feature unification will otherwise turn `no_std` on for someone who wanted the opposite. `cargo hack --feature-powerset check` is how you find out whether any of this is true. `compile_error!` is the right tool where that restructuring is not possible, and inside declarative/procedural macros to reject invalid invocations with a readable message
- **ARCH-13.** Code ported from C#, Java, C++, or Python must be reshaped, not transliterated. Separate the two halves of a port: the *domain* logic — a pricing rule, a parser, a state machine — should come across nearly unchanged, while the *language* scaffolding around it should not survive at all, because it exists to solve problems the source language has and Rust does not. Scan signals, each of which usually indicates a mechanical translation: a `throw_if_null` / `check_not_null` helper (Rust has `Option`); an interface-per-service trait implemented exactly once and passed as `dyn` (API-18); `Arc` at every field because the source language boxed everything (PERF-17); a `Manager`/`Service`/`Factory` type (API-1); inheritance simulated through `Deref` (OWN-12); a global registry or singleton static (CONC-10); exceptions modelled as panics (ERR-11); manual `Dispose`-style teardown methods where `Drop` belongs. The most deceptive cases are the constructs that *do* translate superficially and diverge later — statics, reflection substitutes, lifetime-free object graphs. A striking structural resemblance between the Rust and the original is the finding, not the achievement
- **ARCH-14.** In an FFI project, business logic lives in the core crate and the FFI crate only translates. `foo` should be ordinary, safe, testable Rust that knows nothing about C; `foo-ffi` owns the `extern "C"` entry points, the raw pointers, the ownership handoffs, and the error-code mapping (SEC-34--36, SEC-39). The failure mode is letting interop requirements leak inward — `#[repr(C)]` on a domain type, a struct flattened into `(ptr, len, capacity)` fields, an owned `Vec` replaced by a raw pointer — which makes the core crate untestable in Rust terms and pins its data model to a foreign ABI forever. Accept the duplication: an FFI entry point that collapses several core calls into one C-shaped function is the correct shape, not a smell. Two conventions ride along: name crates by direction (`-sys` for bindings *into* an existing C library, `-ffi` for a Rust library exported *to* C), and where a type wraps a native handle, provide `unsafe fn from_native(h) -> Self` plus `to_native`/`into_native` escape hatches with their contracts documented, so a caller holding a handle from elsewhere is not forced to fork the crate
- **ARCH-15.** Workspace layout: one `Cargo.toml` at the root, all crates as siblings in a single directory (`crates/`), and a shallow grouping (`common/`, `server/`, `client/`) only past a dozen or two. A crate nested inside another crate's directory — worst of all inside its `src/` — is never right; express the relationship with a name prefix instead (`foo`, `foo_core`, `foo_proc`). **When in doubt, split.** Rust compiles a crate as a unit, so a large crate serializes work that separate crates parallelize and recompile independently; if a submodule could stand on its own, it should be its own crate. The split also breaks `pub(crate)` shortcuts, which is usually the design feedback you wanted. Re-join for the user with an umbrella crate where the split was purely technical (a `foo_proc` proc-macro crate must be re-exported from `foo`, MACRO-3). Rule of thumb for the crate-versus-feature choice: a **crate** is for functionality that can be used on its own; a **feature** unlocks functionality that cannot
- **ARCH-16.** A published library must build with nothing but `cargo` and `rustc`. Users install crates whose dependency trees run into the hundreds and expect `cargo build` to just work — so a crate that needs `perl`, `cmake`, cross-compilers, a `protoc` binary, or an environment variable to compile imposes that on every transitive consumer, most of whom have never heard of it. Run code generation (protobuf, bindgen, parser generators) at *publish* time and ship the generated `.rs` files in the crate. Unless the crate is obviously platform-specific, it must build on all Tier 1 targets — introduce an internal HAL module with a `dummy` fallback rather than `#[cfg]`-ing a hole into the build. For a `-sys` crate wrapping a native library: drive the build from `build.rs` via the `cc` crate rather than invoking Makefiles or shell scripts, vendor the upstream sources into the crate (recording the git URL and hash so they are verifiable), make optional tools like `nasm` genuinely optional, pre-generate the `bindgen` glue, and support dynamic loading (`libloading`) alongside static linking. Where sources are too large for crates.io and must be downloaded, pin their hashes and allow an env-var override of the source root so hermetic builds are still possible
- **ARCH-17.** A **new** crate or workspace should be created on the latest stable edition (2024 at the time of writing); the `resolver` key is implied by the edition and not needed. Unlike an MSRV bump (API-15) this costs nothing in compatibility — editions are per-crate, and a 2015-edition binary links 2024-edition libraries without issue — so an old edition on new code buys nothing and locks the crate out of let-chains (FN-2), `gen`, the `unsafe_op_in_unsafe_fn` default, and the 2024 match-ergonomics rules. Scope: this is about the edition a crate is *created* on. Migrating an existing crate is the compiler's and `cargo fix --edition`'s job and is not a finding — see the `EDITION-*` reference notes in rules-core.md
- **ARCH-18.** Never write `#![deny(warnings)]` in the source. It makes every future rustc release a potential build break: new lints, newly `#[deprecated]` APIs, and lints promoted from allow to warn all become hard errors in code that compiled yesterday, and nobody can build the crate with an extra lint set (clippy included) without editing it. Keep the build setting out of the code — `RUSTFLAGS="-D warnings"` in CI, where a break is your break on a toolchain you chose to bump — and in the source deny only the specific lints the crate genuinely depends on (`unsafe_code`, `missing_docs`, `unused_must_use`, `clippy::unwrap_used`), declared once through `[workspace.lints]`/`[lints]` rather than as crate-root attributes (ARCH-11). Cargo's `--cap-lints` spares *consumers* of a published crate from this, so the damage lands on your own CI, your contributors, and anyone building from git
