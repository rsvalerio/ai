# Security Rules

## Security: Memory Safety (typical severity: Critical)

- **SEC-1.** No use-after-free, double-free, or data races (safe Rust prevents these at compile time; verify unsafe blocks and atomic orderings manually)
- **SEC-2.** Validate all raw pointer dereferences; document safety invariants
- **SEC-3.** No bad `transmute`; prefer safe casts (`as`, `From`/`Into`)
- **SEC-4.** Verify `Send`/`Sync` bounds on types shared across threads

**Detection heuristics** — search for: raw pointer dereferences without bounds checking or null validation, `std::mem::uninitialized()` (deprecated, use `MaybeUninit`), use-after-free patterns and double-free risks, missing `Send`/`Sync` bounds on types crossing thread boundaries, `transmute` between incompatible types without validation, dangling references in unsafe blocks.

> SEC-1--4 own the **security** angle of unsafe code. UNSAFE-1--8 cover the **idiomatic** angle. When both apply, use a single finding under the SEC prefix and note idiomatic concerns in the Notes section.

## Security: Secrets & Crypto (typical severity: High--Critical)

**Detection heuristics** — search for: hardcoded strings matching key/password/token patterns, `Debug` derive on types containing secrets, missing `zeroize`/`secrecy` crate usage for sensitive data, weak algorithms (MD5, SHA1, DES, RC4) in crypto contexts, IV/nonce reuse patterns, non-CSPRNG sources for security values.

- **SEC-5.** Secret types: disable `Debug`/`Clone`, auto-zeroize on drop. **`Serialize` is the half that gets forgotten** — a derived `Serialize` writes the secret into every JSON response, cache entry, and audit record the type reaches, and unlike `Debug` it is rarely thought of as a debugging affordance; it needs the same treatment (SEC-21). Where the enclosing type must stay printable, redact the *field* rather than suppressing the whole impl: give the secret its own newtype whose `Debug` writes `[REDACTED]`, and the outer struct keeps a useful `#[derive(Debug)]`. A hand-written `Debug` must **destructure `self`** rather than reach through `self.field` — `let DatabaseUri { scheme, user, password: _, host, database } = self;` stops compiling when a field is added, whereas the field-access form silently keeps printing the old subset, so a newly added secret is either leaked or omitted forever depending on which mistake was made. Both directions of that failure are why the destructuring form is the review check
- **SEC-6.** The `secrecy` crate packages redaction and zeroization together and is the default choice over a hand-rolled wrapper (SEC-5). **Name the type by crate version**: `secrecy::Secret<T>` on 0.8, renamed to `SecretBox<T>` in 0.10 with `SecretString` retained as an alias; reading the value is always an explicit `expose_secret()` call, which is the point — the exposure is greppable. Verify the name against the version in `Cargo.toml` before filing
- **SEC-7.** Constant-time comparisons for sensitive data (use `subtle::ConstantTimeEq` from the `subtle` crate)
- **SEC-8.** No hardcoded keys, passwords, tokens, or NKey seeds in source or VCS; use environment variables or secret managers
- **SEC-9.** No weak algorithms (MD5/SHA1/DES) for cryptographic or security purposes; use modern alternatives (SHA-256+, AES, ChaCha20). Use AEAD modes (AES-GCM, ChaCha20-Poly1305) for authenticated encryption — unauthenticated encryption without HMAC is a finding. For password hashing/key derivation, use Argon2, scrypt, or PBKDF2. Non-security uses of SHA1 (e.g., content-addressable storage, git interop) are acceptable when clearly documented. **Common crypto antipatterns**: (1) IV/nonce reuse across encryptions (breaks CBC, CTR, GCM security), (2) weak password hashing (bcrypt with cost <10, plain SHA-256), (3) unauthenticated encryption (AES-ECB, CBC without HMAC), (4) non-CSPRNG for secrets (see SEC-10)
- **SEC-10.** Prefer the OS-entropy RNG for key generation, security tokens, and any cryptographic use. **Name by `rand` version**: on `rand` ≤ 0.9 this is `OsRng` (`rand::rngs::OsRng`); on `rand` 0.10+ `OsRng` was **renamed to `SysRng`** (`rand::rngs::SysRng`, re-exported from `getrandom`) — fill via `rand::TryRng::try_fill_bytes(&mut SysRng, &mut buf)` (fallible: OS entropy can fail), or call `getrandom::fill(&mut buf)` directly. A 0.10+ codebase referencing `OsRng` will not compile. For non-cryptographic unpredictable randomness (shuffling, jitter), use `rand::rng()` on `rand` 0.9+ (current default) or the legacy `thread_rng()` on 0.8 — both are CSPRNG-backed. Never use `SmallRng` or other non-CSPRNG sources for security-sensitive values. In tests, use fixed-seed RNGs for determinism (TEST-16). **Maintenance**: the `rand` API surface changes across major versions — verify names against current crate docs when auditing

## Security: Input Validation (typical severity: High--Critical)

**Detection heuristics** — search for: string concatenation in SQL/command construction, `format!` with user input in shell commands, missing size/depth limits on deserialization, unchecked `as` casts between integer types, user-controlled regex without size bounds, path operations without canonicalization or root validation.

- **SEC-11.** Validate and sanitize all external input at system boundaries using layered validation: (1) type validation — reject wrong types early, (2) range/size — enforce bounds on numeric values and collection sizes, (3) format — validate patterns, encoding, and structure, (4) business rules — domain-specific constraints (e.g., age ≥ 0, email format). When deserializing untrusted data (serde, protobuf), enforce size limits and max nesting depth, validate schema, and reject unknown fields in security-critical contexts
- **SEC-12.** Parameterized queries for SQL; no string concatenation
- **SEC-13.** Sanitize command arguments; no shell interpolation (`Command::new` over `sh -c`). `std::process::Command` does not invoke a shell, so a value passed through `.arg()` is delivered to the child as one argv entry and its metacharacters (`;`, `|`, `$`, backticks) are inert — the injection risk appears only when the code builds a string and hands it to `sh -c` or `cmd /C`. **`.arg()` is not the end of the review, though: it stops *command* injection and not *argument* injection.** A user-controlled value that begins with `-` is still parsed as a flag by the child, so a "filename" of `--output=/etc/cron.d/x` or `-o` changes what the program does rather than what it reads — the classic cases are `--upload-file` on `curl`, `-e` on `ssh`, `--exec` on `find`, and `-o` on any compiler. Fix at the callsite: pass the conventional `--` end-of-options separator before user-supplied operands where the program honours it, prefix relative paths with `./`, and reject or reject-and-report a leading dash otherwise (SEC-11's allowlist is the durable form). Two more inherited surfaces: the child inherits the parent's environment unless `.env_clear()` is called, so `LD_PRELOAD`, `PATH`, `IFS`, and `BASH_ENV` reach it from wherever the parent got them; and a bare program name is resolved through `PATH`, so pass an absolute path for anything security-relevant. Set `.current_dir()` explicitly rather than depending on the process's cwd
- **SEC-14.** Path traversal: canonicalize and validate paths against allowed roots. **`Path::join` is the specific trap**: joining an *absolute* segment replaces the base rather than extending it, so `Path::new("/srv/uploads").join(user_input)` evaluates to `/etc/shadow` when `user_input` is `/etc/shadow` — no error, no panic, and nothing in the expression that looks wrong. The behaviour is deliberate (it lets a caller pass either a relative or an absolute path and have the callee absolutize only the former), which is exactly why it survives review; `PathBuf::push` behaves the same way. Treat any `join`/`push` of an externally-supplied segment as a traversal finding unless the segment is first rejected for `is_absolute()` and for `Component::RootDir` / `Component::ParentDir` / `Component::Prefix` — checking for the literal string `".."` is not enough, since encoding and separator variants slip past it — and the joined result is still canonicalized and confirmed to start with the allowed root. `clippy::join_absolute_paths` fires only on a literal argument, so it is a floor, not the check. **`canonicalize` only works on paths that already exist**, which is the half most often missed: for a file the code is about to *create*, canonicalizing the target returns `NotFound` and the check is typically dropped or, worse, turned into a fail-open. Canonicalize the **parent** directory instead and confirm *that* starts with the allowed root, then join the single validated final component. Note also that canonicalization resolves symlinks at the moment it runs, so a check followed by a separate open is a TOCTOU window (SEC-25) — where the path is attacker-influenced and the operation matters, open a handle and operate through the descriptor rather than re-resolving the path
- **SEC-15.** Integer overflow: use checked/saturating arithmetic for untrusted input; audit `as` casts between integer types for truncation (e.g., `u64 as u32`); prefer `try_from`/`try_into` which return `Result` on overflow. **Critical audit detail**: Rust checks for overflow in debug mode (panics) but wraps silently in release mode by default — code that "works" in dev can overflow in production; use `checked_*`/`saturating_*`/`wrapping_*` methods to make overflow behavior explicit regardless of build profile. The choice among the three is a statement of intent, not a way to quiet a warning: `checked_*` where the caller must handle the case, `saturating_*` where clamping is the correct answer, `wrapping_*` only where wraparound *is* the semantics (hashes, sequence numbers, PRNGs). Where the workload can absorb the cost, `overflow-checks = true` under `[profile.release]` restores the debug-mode panic in release builds — a panic is not a fix, but it converts silent corruption into a loud, locatable failure, which is the right trade on anything computing money, sizes, or offsets. Overflow the compiler can *see* is already a hard error in every profile (`arithmetic_overflow` is deny-by-default), so this only concerns values it cannot constant-fold. For the `as` half of the rule, pick by whether loss is possible: `From`/`Into` when the conversion is provably lossless (`i32` → `i64`), `TryFrom`/`TryInto` when it is not, and `as` only where truncation is intended and documented — it silently discards the high bits (`0x1234u16 as u8 == 0x34`) and saturates rather than erroring on float→int. `clippy::cast_possible_truncation`, `cast_sign_loss`, `cast_possible_wrap`, and `cast_precision_loss` catch these mechanically (ARCH-11)
- **SEC-16.** Regex limits — but be precise about which risk applies, because the generic ReDoS advice misdescribes the Rust ecosystem. The `regex` crate uses finite automata and **guarantees linear time in the length of the haystack**, with no backtracking, so the catastrophic-backtracking ReDoS familiar from PCRE, Python, and JavaScript does not exist there — and it is why `regex` deliberately omits backreferences and lookaround. Recommending a rewrite "to avoid ReDoS" on a `regex`-based matcher is a false finding. The risks that *do* apply: (1) **compiling an untrusted pattern.** A user-supplied regex is an untrusted program — its compiled automaton can be enormous — so build it through `RegexBuilder` with an explicit `size_limit` and `dfa_size_limit` rather than `Regex::new`, and cap the pattern's own length first. (2) **Compiling in a loop.** `Regex::new` inside a request handler or an iterator body recompiles per call; hoist it into a `LazyLock` (CONC-10) or `OnceLock`. (3) **Crates that are not `regex`.** `fancy-regex` (backreferences, lookaround) and any binding to PCRE, Oniguruma, or a JS engine *are* backtracking and do carry classic ReDoS — the same pattern is safe in one crate and a DoS in the other, so identify the crate before filing. Haystack size is still bounded by SEC-33 in every case
- **SEC-33.** Bound resource consumption on untrusted input: enforce size limits on buffers, collections, and strings; cap iteration counts; set timeouts on operations processing external data — prevents DoS via unbounded allocations or infinite loops. Three shapes are worth naming because each looks bounded and is not:
  - **Pre-allocation from a wire-supplied length.** `Vec::with_capacity(hdr.count)` or `String::with_capacity(n)` allocates *before* a single byte of the payload has been read or validated, so a four-byte length field is a remote request for gigabytes — and it is the same defect whether the peer ever sends the data. Validate the length against a `MAX_*` constant first, or size the buffer to what has actually arrived and let it grow (PERF-2's advice is for trusted sizes). The related trap is a `read_to_end`/`read_to_string` on a socket or an HTTP body with no cap: use `Read::take(limit)` / the framework's body-size limit.
  - **Decompression ratio.** A gzip, zstd, or zip stream is bounded on the wire and unbounded after inflation — a megabyte can expand to gigabytes, so a size limit on the *request* bounds nothing about memory. Decompress through a `take`-limited reader and fail when the limit is hit, and reject archives whose declared ratio is implausible before starting.
  - **Depth limits are not size limits.** `serde_json` caps recursion depth (128 by default), which stops a deeply-nested document from blowing the stack and stops nothing else: a flat 100 MB array of small objects passes the depth check and allocates everything. Cap the byte length at the transport, and prefer streaming or a bounded reader over deserializing straight into an owned collection. Untagged and `#[serde(flatten)]` variants also cost backtracking work per element, which multiplies whatever the size limit permits

## Security: Access Control (typical severity: High--Critical)

- **SEC-17.** Encode auth states in enums; compiler enforces all cases
- **SEC-18.** Check authorization at every entry point; no implicit trust
- **SEC-19.** Prevent IDOR: validate resource ownership before access
- **SEC-20.** Tenant isolation: enforce boundaries in multi-tenant systems

## Security: Information Disclosure (typical severity: High)

**Detection heuristics** — search for: `Debug` or `Display` impls that format secret fields, `tracing::info/debug/error!` or `log::` calls with connection strings or credentials, error messages returning internal paths or stack traces, `panic!` messages containing sensitive context.

- **SEC-21.** No secrets, stack traces, or internal-path details in log output, error messages returned to users, or error chains (covers both logging and error-type leakage; see also ERR-1--10 for idiomatic error handling). Map internal errors to public error types at system boundaries (ERR-7)
- **SEC-22.** No fingerprinting surface on user-facing responses: do not expose server versions (`Server:` header, banner), library versions, OS details, build hashes, or feature flags. These aid reconnaissance and CVE targeting. Fix: strip or override framework-default identifying headers; route verbose errors to structured logs, not responses
- **SEC-23.** Disable debug endpoints and verbose logging in production; gate behind explicit `cfg(debug_assertions)` or feature flags, not environment variables that can be toggled by an attacker

## Security: Concurrency (typical severity: High--Critical)

**Detection heuristics** — search for: `unsafe impl Sync` or `unsafe impl Send` (verify manually), `RefCell` in types shared across threads, file/resource check-then-use patterns (TOCTOU), inconsistent lock ordering across functions, callback or async handler code that mutates shared state without guards.

- **SEC-24.** In `unsafe impl Sync`/`Send`, verify no `RefCell<T>` is exposed across threads — `RefCell<T>` is `!Sync` by design and safe Rust prevents cross-thread use at compile time; this is only reachable via manual `unsafe impl`. Use `Arc<Mutex<T>>` or `Arc<RwLock<T>>` instead (see OWN-10 for idiomatic usage)
- **SEC-25.** TOCTOU (time-of-check-to-time-of-use) in file/resource operations: any `metadata()`/`exists()`/`access()` check followed by an independent open/read/write is racy — the filesystem can change between the two calls. Fix: perform the operation directly and handle errors (e.g., `OpenOptions::new().create_new(true).open(path)` instead of "check then create"), use `openat`/handle-based APIs where available, and prefer `std::fs::File::options()` primitives that atomically combine check and act. The canonical shape is a **symlink swap**: `path.is_dir()` succeeds, an attacker replaces `path` with a symlink pointing somewhere they do not own, and the recursive delete or write that follows resolves the path a second time and follows it. This is CVE-2022-21658 in `std::fs::remove_dir_all` — the standard library got it wrong, so "we reviewed it carefully" is not a defence. The structural fix is to **acquire a handle first and then check the handle**, never to re-resolve the path: open with `O_NOFOLLOW | O_DIRECTORY` via `std::os::unix::fs::OpenOptionsExt::custom_flags` so the open itself fails on a symlink or a non-directory, then perform every subsequent operation through that descriptor (the `openat` family, or the `cap-std` / `rustix` wrappers, which make the handle-relative style the default rather than an opt-in). Once the handle is open, the entry it names cannot be substituted underneath you
- **SEC-38.** Reentrancy in callbacks, signal handlers, and async state machines: state mutation during a nested/reentrant call can bypass invariants the outer call assumed (e.g., a handler that recurses into itself via an event loop, or an async task re-entering a state machine while it's still being updated). Fix: encode valid transitions as a typestate or enum-state machine and reject calls in wrong states; or install a reentrancy guard (e.g., `AtomicBool` flag set on entry, cleared on exit, with nested entry rejected or deferred); never mutate shared state while dispatching callbacks that may re-enter
- **SEC-26.** Treat deadlock as a DoS vulnerability on request-handling paths: a single attacker-triggered lock-order inversion or await-holding-guard can freeze a worker pool. Enforce a documented global lock order for locks that can be held together, prefer `try_lock`-with-backoff for optional locks, and never hold a `Mutex`/`RwLock` guard across an `.await` (see CONC-2). Audit for: (1) two locks acquired in different orders in different code paths, (2) guards held across `.await`, (3) recursive locking of non-reentrant locks

## Security: FFI (typical severity: High--Critical)

- **SEC-34.** Validate all raw pointers at FFI boundaries before dereferencing; document caller invariants ("caller must ensure buffer is initialized and valid for N bytes")
- **SEC-35.** Never use `std::mem::uninitialized()` (deprecated, instant UB); use `MaybeUninit` instead
- **SEC-36.** Audit FFI bindings for correct nullability, lifetime, and ownership transfer semantics; verify function signatures match C expectations (ABI, calling convention, signedness)
- **SEC-39.** Treat every exported symbol as global namespace. `#[unsafe(no_mangle)]` publishes a function or static under its bare Rust name, so two crates in one link unit that both export `init` collide — either a link error or, with dynamic linking and symbol interposition, the wrong function silently wins. Review checks: (1) prefix exported names with the crate or project (`#[unsafe(export_name = "mylib_init")]`) rather than relying on a bare `#[unsafe(no_mangle)]` for anything generically named; (2) exported functions must declare an explicit ABI (`pub extern "C" fn`) — the default Rust ABI is unstable and calling it from C is UB; (3) panics must not escape across the boundary — since Rust 1.71 an unwind out of `extern "C"` aborts the process rather than being UB, which turns a recoverable error into a crash, so wrap fallible bodies in `std::panic::catch_unwind` and convert to an error code, or use `extern "C-unwind"` when the foreign caller genuinely expects to propagate unwinding. Both attributes require the `unsafe(...)` wrapper in the 2024 edition (UNSAFE-7)

**FFI audit checklist**: For each FFI boundary, verify: (1) all returned raw pointers null-checked before deref, (2) caller invariants documented on every `unsafe fn`, (3) no `std::mem::uninitialized()` (use `MaybeUninit`), (4) ownership transfer semantics clear (who frees?), (5) lifetime validity of pointers across calls, (6) exported symbols namespaced and panic-safe (SEC-39)

- **SEC-40.** Across a boundary between two Rust dynamic libraries (or between a DLL and its host), only **portable** data may be exchanged — a strict subset of FFI-safe. rustc compiles each dynamic library as an independent artifact: a crate statically linked into two artifacts is instantiated separately in each, so its `static` and `thread_local!` items exist once per artifact rather than once per process (CONC-10) — sharing them requires every side to go through one shared dynamic library, which is not the default and cannot be assumed. Neither `TypeId` values nor the layout of any `#[repr(Rust)]` type is guaranteed to agree between two independent compilations — both are unspecified and free to differ. Passing a `String`, `Vec<u8>`, `Box<T>`, or any non-`#[repr(C)]` struct between two such libraries therefore rests on guarantees the language does not make. Be precise about the failure mode when reviewing, because it is not deterministic and the overstated version of this rule gets dismissed: built from one toolchain with matching flags and a shared allocator, the layouts usually *do* agree and the code appears to work, which is exactly what makes it dangerous. It breaks once anything diverges — one library rebuilt on a different compiler version, different codegen flags, one side installing a `#[global_allocator]` — and the symptoms are then misread fields and heap corruption on free rather than a clean error at the boundary. The same applies to anything routed through a `TypeId` (`dyn Any` downcasts, type-keyed registries), and anything that touches a runtime relying on statics (`tokio`, `log`, `tracing` subscribers) on the far side. Portable means `#[repr(C)]` (or otherwise layout-guaranteed) **and** no interaction with any static, thread-local, or `TypeId`, **and** containing no pointer or reference into non-portable data. Note the trap the signature hides: a `&CommonService` argument is UB if any type nested inside it differs in layout, and a method called on it *appears* to execute in the callee's library while actually running the caller's code against the callee's data — mixing one library's statics with the other's state. Cross-library sharing must go through a C ABI with owned, `#[repr(C)]` message types and per-library allocation/free entry points (SEC-39, ARCH-14)
- **SEC-41.** Strings crossing the FFI boundary fail in two distinct ways; check both directions. **Outbound**, the `CString` must outlive every use of the pointer, which is *not* the same as outliving the statement. `seterr(CString::new(s)?.as_ptr())` is sound when `seterr` merely reads or copies the bytes before it returns — the temporary is dropped at the end of the full statement, so it is alive for the duration of the call. It is a use-after-free when the callee **retains** the pointer (stores it in a global, a struct, a registered callback) or reads it after returning, because nothing keeps the temporary alive past that statement; bind it first (`let c = CString::new(s)?;`) and keep the binding alive for as long as the C side holds the pointer. So review the callee's contract, not the shape of the expression. Never let the C side *write* through a pointer obtained from `CString::as_ptr()` — it is a `*const c_char`, and mutating the buffer can leave the interior-NUL and terminator invariants `CString` relies on broken (`from_raw` is defined only for a pointer from `into_raw` whose length is unchanged). For an output buffer, pass an initialized `Vec<u8>`, validate the length the callee reports against the capacity you gave it, truncate, and build the string afterwards. **Inbound**, borrow instead of copying: `CStr::from_ptr(p).to_str()` in one small `unsafe` block yields a `&str` with no allocation and no arithmetic, whereas hand-rolled `strlen` + `copy_nonoverlapping` + `set_len` reconstructions are exactly where the missing NUL terminator and the uninitialized tail byte live — a bug that surfaces as "sometimes invalid UTF-8, sometimes a stray character, sometimes a crash". Both directions still owe SEC-34's null and validity check and a `# Safety` section naming what the caller must guarantee
- **SEC-42.** Do not export a handle whose validity depends on another handle's lifetime. `dbm_iter_new(db) -> *mut KeysIter` compiles, but the lifetime tying the iterator to its parent does not survive the boundary: foreign code can close the parent and keep iterating, and neither Rust nor the borrow checker can see it. It is worse than a loud failure — with the parent's memory not yet reused it *usually* works, so the use-after-free reaches production and segfaults occasionally. Fold the borrowed state into the owner and expose stateful operations on it (POSIX DBM's `dbm_firstkey`/`dbm_nextkey`, or a wrapper struct holding the collection plus an `iter_next: usize` cursor), so there is one live pointer and one lifetime. This is also an **aliasing** rule, not only a use-after-free one: if any exported function can take `&mut` to the collection while a stored iterator exists, that `&mut` is not exclusive and the code is UB even if nothing ever reads the iterator (SEC-24). Never `transmute` a borrowed iterator to `'static` to make a handle API type-check — the supported answers are an owning cursor (index- or key-based) or a snapshot

## Security: Dependencies (typical severity: High)

- **SEC-27.** Review unmaintained or abandoned dependencies; check for known vulnerabilities; vet dependency source trustworthiness (unverified registries, unknown maintainers, weak security track record). Run `cargo audit` (RustSec advisory database) in CI to detect known CVEs in the dependency tree; combine with `cargo outdated` to surface stale dependencies before they reach end-of-life. **The review scope is wider than the runtime dependency tree, because `build.rs` scripts and proc macros execute — with full ambient privileges — on the developer's machine and the CI runner at *compile* time, before any of your code runs and before any test is executed.** A malicious or compromised build script owns the environment it builds in, including whatever credentials the CI job holds, so "it's only a dev-dependency" and "we never call it" are not mitigations: `cargo test`, `cargo check`, and a rust-analyzer save are each enough to run it. Practical checks when a dependency is added or a lockfile diff shows a new transitive one: does it ship a `build.rs` or a proc-macro crate at all (`cargo tree` shows what is really being pulled in, and a new build script in a patch-version bump deserves an explanation); does the crate name match the one intended (typosquats differ by a hyphen/underscore or a single letter — verify the repository link, maintainer, and download history rather than the name alone); and how large is the transitive surface being accepted for the value gained. `cargo vet` records that a human actually reviewed a given crate *version*, which is what turns this from a one-time judgement into a reviewable artifact
- **SEC-28.** Pin dependency versions; ensure `Cargo.lock` is committed (missing lockfile allows silent dependency drift); audit lockfile changes in PRs; consider `cargo-deny` for license and security policy enforcement via a `deny.toml` covering advisories, allowed licenses, duplicate versions, wildcard requirements, and permitted sources (`unknown-registry`/`unknown-git` set to `deny` keeps dependencies from anywhere but the intended registry). **Committing the lockfile is only half of it — CI must also build with `--locked`**, which fails the build if `Cargo.lock` would need to change, rather than silently re-resolving to versions nobody reviewed; a committed lockfile that every job quietly updates provides no more assurance than none. For deployed binaries, `cargo auditable` embeds the resolved dependency list into the artifact, so "is *this* running binary affected by the advisory published today?" is answerable from the binary itself instead of from a guess about which commit produced it

## Security: Configuration (typical severity: High)

- **SEC-29.** Secure defaults: TLS enabled, auth required, debug disabled; verify configuration file permissions are not world-readable
- **SEC-30.** Validate configuration at startup; fail fast on insecure settings; implement secret rotation mechanisms and key expiration where applicable

## Security: Error Handling (typical severity: High)

- **SEC-31.** No security bypass on error; fail closed
- **SEC-32.** Ensure cleanup of sensitive resources on error paths

## Security: Testing & Verification (typical severity: Medium--High)

- **SEC-37.** Fuzz security-critical parsing and deserialization code with fuzzing tools; prioritize code that handles untrusted input, protocol parsing, and format conversion
